Was ist RBAC? Role-Based Access Control mit Beispielen

Was ist RBAC?​

Rollenbasierte Zugriffskontrolle (RBAC) gewährt Berechtigungen Rollen statt einzelnen Benutzern und weist jedem Benutzer eine oder mehrere Rollen zu. Um einem neuen Mitarbeiter seine Arbeit zu ermöglichen, weisen Sie ihm eine Rolle wie editor oder billing zu; um zu ändern, was alle Editoren tun können, ändern Sie die Rolle einmalig.

RBAC besteht aus drei Teilen:

  • Benutzer: Personen oder Dienste, die Anfragen stellen.
  • Rollen: Benannte Funktionsrollen, wie admin, editor oder viewer.
  • Berechtigungen: Eine Aktion auf einer Ressource, wie edit auf /articles.

Eine Anfrage wird erlaubt, wenn eine der Rollen des Benutzers die Berechtigung besitzt. Rollen können auch von anderen Rollen erben: Wenn editor von viewer erbt, erhalten Editoren alles, was Viewer tun können. RBAC wurde in den 1990er Jahren von NIST formalisiert, und die RBAC96-Familie von Modellen beschreibt die Varianten: flache Rollen, Rollenhierarchien und Einschränkungen. Siehe RBAC vs. RBAC96, wie Casbin diese abbildet.

Ein minimales RBAC-Modell und eine Richtlinie in Casbin:

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
p, editor, article, edit
p, viewer, article, read

g, editor, viewer
g, alice, editor
g, bob, viewer

alice darf Artikel bearbeiten und lesen (editor erbt viewer); bob darf sie nur lesen.

RBAC is easy to audit but cannot say "only their own records" without creating a role per record. ABAC adds conditions on attributes such as the owner or the time of day, and most applications combine both. Choosing an access control model compares ACL, RBAC, ABAC and ReBAC on one example.

Tutorials: Fügen Sie RBAC zu einer Web-API hinzu in Go mit Gin, Node.js mit Express, NestJS, Python mit FastAPI, Java mit Spring Boot, Rust oder gRPC. Sie können auch die RBAC-Beispiele im Online-Editor ausprobieren.

Rollendefinition​

Der Abschnitt [role_definition] definiert RBAC-Rollen(erblichkeits-)Beziehungen. Casbin kann mehrere RBAC-Systeme gleichzeitig betreiben: eines für Benutzer (mit Rollenererbung) und optional eines für Ressourcen. Jedes ist unabhängig.

Dieser Abschnitt ist optional; lassen Sie ihn weg, wenn Sie kein RBAC verwenden.

[role_definition]
g = _, _
g2 = _, _

Hier sind g und g2 zwei Rollensysteme; _, _ bedeutet, dass jedes zwei Seiten hat (z. B. Benutzer und Rolle). Verwenden Sie nur g für Benutzerrollen; fügen Sie g2 hinzu, wenn auch Ressourcen Rollen haben. Beispiele: rbac_model.conf, rbac_with_resource_roles_model.conf.

Benutzer–Rolle- (und Ressourcen–Rolle-)Zuordnungen werden in der Richtlinie gespeichert, zum Beispiel:

p, data2_admin, data2, read
g, alice, data2_admin

Also hat alice die Rolle data2_admin. Casbin behandelt alle Namen als Strings (Benutzer, Ressource oder Rolle).

Verwenden Sie die Rolle in einem Matcher:

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act

Die Anfrage ist also nur erlaubt, wenn das Subjekt der Anfrage die in der Richtlinie angegebene Rolle besitzt.

Notiz
  1. Casbin speichert und evaluiert nur Benutzer–Rolle- (und Ressourcen–Rolle-)Zuordnungen; es validiert nicht, ob Benutzer oder Rollen existieren. Das ist Aufgabe der Authentifizierung.
  2. Do not reuse the same name for a user and a role (e.g. user alice and role alice), since Casbin cannot tell them apart. Use typed names to keep them apart.
  3. Die Rollenerbung ist transitiv und unbegrenzt: Wenn A die Rolle B hat und B die Rolle C hat, dann hat A effektiv die Rolle C.
Konvention für Token-Namen

Das Subjekt in der Richtlinie wird normalerweise sub genannt und steht an erster Stelle. In Go Casbin können Sie andere Namen und Reihenfolgen verwenden; dann müssen Sie nach dem Erstellen des Enforcers e.SetFieldIndex("p", constant.SubjectIndex, index) aufrufen, damit APIs wie DeleteUser die richtige Spalte verwenden.

# `subject` here is for sub
[policy_definition]
p =  obj, act, subject
e.SetFieldIndex("p", constant.SubjectIndex, 2) // index starts from 0
ok, err := e.DeleteUser("alice") // without SetFieldIndex, it will raise an error

Benannte Rollensysteme und Berechtigungsabhängigkeiten​

g, g2, g3, ... sind unabhängige Rollensysteme. Jedes definiert einen Graphen, den der Matcher unter demselben Namen aufruft; g2 ist keine eingebaute "Berechtigung hängt von Berechtigung ab"-Relation. Eine Zeile wie g2, edit, read ist nur eine Kante — sie ändert eine Entscheidung nur, wenn der Matcher g2(...) abfragt.

Das ist wichtig, wenn Ihr Berechtigungskatalog Abhängigkeiten hat, zum Beispiel "edit impliziert read", sodass eine Rolle, die bearbeiten darf, auch lesen dürfen muss. Es gibt zwei saubere Möglichkeiten, dies zu modellieren.

Verwenden Sie Rollenererbung, wenn die Abhängigkeit Teil der Autorisierung ist. Geben Sie jedem Bündel eine Rolle und lassen Sie die Rollen erben:

p, editor, article, edit
p, viewer, article, read

g, editor, viewer
g, alice, editor

alice kann lesen, weil editor viewer erbt; g2 ist nicht involviert.

Verwenden Sie einen separaten g2-Graphen, wenn die Abhängigkeit selbst in der Richtlinie sein soll. Der Matcher definiert die Bedeutung:

[role_definition]
g = _, _
g2 = _, _

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && (r.act == p.act || g2(p.act, r.act))
p, admin, article, write
g2, write, read
g, alice, admin

Die Anfrage alice, article, read entspricht der Zeile p, admin, article, write, weil g2(write, read) wahr ist: write ist ein Kind von read, die gleiche Richtung wie g-Kanten. g2-Zeilen gewähren nichts eigenständig und werden von Casbin nicht validiert; Sie bestimmen die Richtung und die Bedeutung jeder Kante, während Casbin dieselbe transitive Vererbung wie bei g anwendet.

Wenn die Abhängigkeit nur Metadaten im Katalog ist — sagen wir, eine Rolle editor sollte "read" vor-auswählen in der Admin-UI, wenn jemand "edit" anhakt — behalten Sie es im Berechtigungskatalog und expandieren Sie es in p-, g- oder g2-Zeilen, wenn Sie die Richtlinie generieren. Casbin muss keine Daten speichern, die nie evaluiert werden. Die Richtlinie muss auch nicht in einer CSV-Datei leben: Ein Adapter kann die generierten Zeilen aus einer Datenbank oder aus Ihrem YAML/JSON-Katalog laden, sodass der Katalog die Quelle der Wahrheit bleibt. Siehe Adapter für die Adapter-API.

Rollenhierarchie​

Casbin implementiert eine Rollenhierarchie im RBAC1-Stil: Wenn alice role1 hat und role1 role2 hat, dann hat alice effektiv role2 und dessen Berechtigungen.

Die Hierarchietiefe gibt an, wie viele Vererbungsebenen Sie zulassen. Der Standard-Rollenmanager verwendet eine maximale Tiefe von 10 (konfigurierbar), sodass ein Benutzer bis zu 10 Ebenen von Rollen erben kann.

// NewRoleManager is the constructor for creating an instance of the
// default RoleManager implementation.
func NewRoleManager(maxHierarchyLevel int) rbac.RoleManager {
    rm := RoleManager{}
    rm.allRoles = &sync.Map{}
    rm.maxHierarchyLevel = maxHierarchyLevel
    rm.hasPattern = false

    return &rm
}

Unterscheidung zwischen Benutzern und Rollen​

In Casbin, users and roles are both strings. In flat RBAC (no role hierarchy), GetAllSubjects() and GetAllRoles() return the left and right sides of g rules (often users and roles). With a hierarchy, the same name can appear as both user and role.

Da Namen einfache Strings sind, werden zwei Entitäten unterschiedlicher Art mit demselben Namen als dasselbe Subjekt betrachtet. Wenn die Namen von Benutzern stammen, führt dies zu einer Rechteausweitung: Ein Benutzer, der sich als admins registriert, erhält alle Berechtigungen der Gruppe admins, und eine Organisation namens acme_t_dev erhält die Berechtigungen des Teams dev in acme, wenn Teamnamen nach dem Muster <org>_t_<team> aufgebaut sind.

Verwenden Sie TypedName, um jedem Namen seinen Typ zuzuweisen. Unterschiedliche Typen oder Teile führen immer zu unterschiedlichen Namen, da %, : und / darin escaped werden:

casbin.TypedName("user", "admins")      // user:admins
casbin.TypedName("group", "admins")     // group:admins
casbin.TypedName("team", "acme", "dev") // team:acme/dev
casbin.TypedName("org", "acme_t_dev")   // org:acme_t_dev
casbin.TypedName("org", "acme/dev")     // org:acme%2Fdev

Verwenden Sie typisierte Namen sowohl beim Schreiben von Richtlinien als auch bei der Durchsetzung (Enforcement):

e.AddPolicy(casbin.TypedName("group", "admins"), "data1", "write")
e.AddGroupingPolicy(casbin.TypedName("user", "bob"), casbin.TypedName("group", "admins"))

ok, err := e.Enforce(casbin.TypedName("user", username), "data1", "write")

ParseTypedName gibt den Typ und die Teile eines typisierten Namens zurück, und FilterTypedNames behält die Namen eines bestimmten Typs bei, beispielsweise die Teams unter den Rollen eines Benutzers:

roles, err := e.GetImplicitRolesForUser(casbin.TypedName("user", "bob"))
teams := casbin.FilterTypedNames(roles, "team")

Implizite Rollen und Berechtigungen​

Rollen und Berechtigungen, die über die Hierarchie vererbt werden (nicht nur direkte Zuweisungen), werden als implizit bezeichnet. Verwenden Sie GetImplicitRolesForUser() und GetImplicitPermissionsForUser(), um sie einzubeziehen; GetRolesForUser() und GetPermissionsForUser() geben nur direkte Zuweisungen zurück. Siehe GitHub #137.

FAQ​

Wofür steht RBAC? Role-based access control. Berechtigungen werden Rollen zugeordnet, Benutzern werden Rollen zugewiesen, und eine Anfrage wird erlaubt, wenn eine der Rollen des Benutzers die Berechtigung besitzt.

Was ist ein Beispiel für RBAC? In der obigen Dokumenten-App darf viewer Artikel lesen und editor sie bearbeiten. Wenn alice die Rolle editor erhält, kann sie lesen und bearbeiten, da editor von viewer erbt; bob, der viewer hat, kann nur lesen. Weder alice noch bob erhalten direkt eine Berechtigung.

Welche Arten von RBAC gibt es? Die RBAC96-Familie beschreibt vier Stufen: RBAC0 umfasst Benutzer, Rollen und Berechtigungen; RBAC1 fügt Rollenhierarchien hinzu; RBAC2 fügt Einschränkungen wie die Trennung von Aufgaben (Separation of Duty) hinzu; RBAC3 kombiniert beides. Casbin implementiert RBAC0 und RBAC1, und Einschränkungen werden als Policy-Zeilen ausgedrückt oder von der Anwendung durchgesetzt. Siehe RBAC vs. RBAC96.

Ist RBAC besser als ABAC? Generell ist keines der beiden Modelle besser. RBAC ist leichter zu prüfen, da eine Rolle auflistet, was sie erlaubt und wer sie besitzt, aber die Formulierung "nur ihre eigenen Datensätze" erfordert eine Rolle pro Datensatz. ABAC wertet Bedingungen auf Attributen wie dem Eigentümer, der Abteilung oder der Tageszeit aus, und die meisten Anwendungen verwenden Rollen für Funktionen und Attributbedingungen für Datensätze.

Ist RBAC noch relevant? Ja. Rollen bleiben die Standardmethode zum Modellieren, welche Funktionen ein Benutzer erreichen kann: NIST hat RBAC in den 1990er Jahren formalisiert, und SSO-Gruppenzuordnungen sowie Cloud-IAM-Rollen folgen weiterhin diesem Modell. ReBAC erweitert es, wenn das Teilen pro Ressource statt pro Rolle erfolgt; es ersetzt es nicht.

Wie füge ich RBAC zu einer Anwendung hinzu? Verwenden Sie eine Autorisierungsbibliothek, anstatt Rollenprüfungen hart zu codieren. In Casbin ist das Modell eine Konfigurationsdatei und die Policy sind Daten, sodass sich Rollen und Berechtigungen ohne erneute Bereitstellung ändern lassen. Vollständige Beispiele finden Sie in den Tutorials für Go, Node.js, Python und Java.
