Casbin (Go) von v2 auf v3 aktualisieren: Ein vollständiges Migrationshandbuch

1. Februar 2026 · 8 Minuten Lektüre
Yang Luo
Creator of Casbin

Wenn Sie Casbin v2 in einer Produktionsumgebung betreiben und sich Gedanken über den Upgrade-Pfad zu v3 machen, ist dieses Handbuch für Sie gedacht. Wir behandeln alles Wissenswerte zum Übergang, von der Einsicht in die Änderungen bis hin zur sicheren Durchführung der Migration in der Produktion.

Was hat sich in v3 geändert?​

Die gute Nachricht: v3 ist primär eine Änderung des Modulpfads mit voller Abwärtskompatibilität. Die Kernlogik für Autorisierung, APIs und Funktionalitäten bleiben unverändert. Dies war eine bewusste Entscheidung, um Störungen zu minimieren, während den semantischen Versionierungsregeln von Go gefolgt wird.

Die Hauptänderung: Modulpfad​

Die einzige Breaking Change in v3 ist der Go-Modulpfad:

// v2
import "github.com/casbin/casbin/v2"

// v3
import "github.com/casbin/casbin/v3"

Das war's. Ihre bestehenden Richtlinien, Modelle und Code-Logiken müssen nicht geändert werden. Die Migration ist mechanisch: Aktualisieren Sie Importanweisungen und Ihre go.mod-Datei.

Warum Release v3?​

Sie fragen sich vielleicht, warum eine neue Major-Version nur für eine Änderung des Importpfads veröffentlicht wird. Die Antwort ist semantische Versionierung. Das Modulsystem von Go verwendet die Major-Versionsnummer im Importpfad (/v2, /v3 usw.). Dies ermöglicht, dass mehrere Major-Versionen in derselben Abhängigkeitsstruktur koexistieren können, was für große Anwendungen mit vielen Abhängigkeiten entscheidend ist.

Durch die Veröffentlichung von v3 haben wir:

  • Uns an die semantische Importversionierung von Go ausgerichtet
  • Eine schrittweise Migration in komplexen Abhängigkeitsgraphen ermöglicht
  • Den Grundstein für zukünftige Erweiterungen gelegt, ohne bestehende v2-Nutzer zu brechen

Was ist gleich geblieben?​

Alles andere. Ernsthaft.

  • Alle APIs bleiben identisch - Enforce(), AddPolicy(), GetAllRoles() und jede andere Methode funktionieren genau wie zuvor
  • Modell- und Richtliniensyntax unverändert - Ihre bestehenden .conf Modell-Dateien und .csv Policy-Dateien funktionieren ohne Modifikation
  • Adapter-Schnittstelle unverändert - Die Methoden von persist.Adapter sind dieselben; Adapter benötigen lediglich eine Release-Build gegen den v3-Modulpfad
  • Leistungsmerkmale - Keine Leistungsregressionen oder -verbesserungen; es ist derselbe Engine
  • Middleware-Integrationen - Middleware funktioniert auf dieselbe Weise, sobald sie dieselbe Major-Version importiert wie Ihr Enforcer

Neue Funktionen in v3​

Seit dem Release von v3.0.0 im Dezember 2025 wurden mehrere neue Funktionen hinzugefügt:

v3.7.0+: Erweiterte Logger-Integration​

Sie können jetzt benutzerdefinierte Logger in die Kern-Durchsetzungsvorgänge und das Policy-Management von Casbin integrieren, was eine bessere Observability bietet:

enforcer.SetLogger(yourCustomLogger)

v3.8.0+: GetAllUsers() API​

Eine neue API, um Benutzer von Rollen zu unterscheiden:

users, err := enforcer.GetAllUsers()

Dies ist besonders nützlich in RBAC-Systemen, wo Sie tatsächliche Benutzer getrennt von Rollendefinitionen auflisten müssen.

v3.9.0+: Eingebaute Zyklenerkennung​

Der Enforcer enthält nun eine automatische Erkennung von Zyklen in Rollenhierarchien, was Endlosschleifen verhindert:

// Automatically detects and prevents circular role assignments
enforcer.AddGroupingPolicy("alice", "admin")
enforcer.AddGroupingPolicy("admin", "alice") // Will be detected as a cycle

v3.10.0+: Explain() API für KI-gestützte Autorisierungseinblicke​

Die neueste Funktion nutzt LLM-APIs, um Autorisierungsentscheidungen in natürlicher Sprache zu erklären:

enforcer.SetAIConfig(casbin.AIConfig{
    Endpoint: "https://api.openai.com/v1/chat/completions",
    APIKey:   os.Getenv("OPENAI_API_KEY"),
    Model:    "gpt-4",
})

explanation, err := enforcer.Explain("alice", "data1", "read")
// e.g. "Alice can read data1 because she has the 'reader' role..."

Dies ist besonders wertvoll für das Debugging komplexer Richtlinien und hilft nicht-technischen Stakeholdern, Autorisierungsentscheidungen zu verstehen.

Migrationsstrategie​

Für neue Projekte​

Einfach: Verwenden Sie von Anfang an v3.

go get github.com/casbin/casbin/v3
import "github.com/casbin/casbin/v3"

Für bestehende v2-Projekte​

Die Migration umfasst drei Schritte:

Schritt 1: Aktualisieren Sie Ihre go.mod​

go get github.com/casbin/casbin/v3
go mod tidy

Schritt 2: Aktualisieren Sie die Import-Anweisungen​

Suchen und ersetzen Sie alle Casbin-Importe in Ihrer Codebasis:

# Using sed on Unix/Linux/Mac
find . -type f -name '*.go' -exec sed -i 's|github.com/casbin/casbin/v2|github.com/casbin/casbin/v3|g' {} +

# Or manually in your editor
# Find: github.com/casbin/casbin/v2
# Replace: github.com/casbin/casbin/v3

Schritt 3: Aktualisieren Sie Adapter-Importe (falls zutreffend)​

Ein Adapter implementiert persist.Adapter aus einer bestimmten Major-Version, da model.Model in casbin/v2 und casbin/v3 unterschiedliche Go-Typen sind. Ein v3-Enforcer benötigt daher eine Adapter-Version, die github.com/casbin/casbin/v3 importiert. Prüfen Sie die go.mod des Adapters:

// Example: the PostgreSQL adapter already depends on casbin/v3
import pgadapter "github.com/apache/casbin-pg-adapter"

// The file adapter is built in and ships with each major version

Wenn Ihr Adapter noch nicht aktualisiert wurde, bleiben Sie für diesen Dienst bei v2, bis dies geschieht, oder eröffnen Sie ein Issue im Repository des Adapters.

Rollback-Plan​

Falls Sie einen Rollback durchführen müssen:

  1. Code-Ebene: Revertieren Sie die Import-Änderungen (verwenden Sie Versionskontrolle)
  2. Abhängigkeits-Ebene: go get github.com/casbin/casbin/v2@latest
  3. Deployment: Nutzen Sie Ihren Standard-Bereitstellungsprozess zum Zurücksetzen

Der Vorteil dieser Migration ist, dass der Rollback trivial ist – einfach die Import-Änderungen zurücknehmen und neu bereitstellen.

Muss ich meine Policy-Datenbank migrieren?​

Nein. Ihre bestehenden Policy-Daten bleiben unverändert. Die Policies werden als einfache Strings gespeichert (Subjekt, Objekt, Aktion usw.) und haben keine Abhängigkeit von der Casbin-Version.

Testen Ihrer Migration​

Automatisiertes Testen​

Ihre bestehenden Tests sollten ohne Änderungen durchlaufen:

func TestPolicyEnforcement(t *testing.T) {
    // This test works identically in v2 and v3
    e, _ := casbin.NewEnforcer("model.conf", "policy.csv")
    
    ok, _ := e.Enforce("alice", "data1", "read")
    if !ok {
        t.Error("Expected alice to have read access to data1")
    }
}

Integrations-testing​

Middleware, die einen *casbin.Enforcer entgegennimmt, ist auf dieselbe Weise wie Adapter an eine Major-Version gebunden. Wenn Ihre Middleware weiterhin casbin/v2 importiert, ist der direkte Aufruf des Enforcers nur wenige Zeilen Code:

// Example with Gin
import (
    "net/http"

    "github.com/casbin/casbin/v3"
    "github.com/gin-gonic/gin"
)

func Authorizer(e *casbin.Enforcer) gin.HandlerFunc {
    return func(c *gin.Context) {
        ok, err := e.Enforce(c.GetString("user"), c.Request.URL.Path, c.Request.Method)
        if err != nil || !ok {
            c.AbortWithStatus(http.StatusForbidden)
            return
        }
        c.Next()
    }
}

Lasttests​

Führen Sie Ihre standardmäßigen Lasttests gegen den v3-Build durch. Die Leistungsmerkmale sollten identisch mit v2 sein.

Policy-Verifizierung​

Vergleichen Sie die Policy-Auswertung über verschiedene Versionen hinweg:

# Export policies from v2
# Load into v3
# Run test cases against both
# Compare results

Wenn Sie Unterschiede feststellen, handelt es sich wahrscheinlich um einen Fehler – bitte melden Sie ihn!

Häufige Fallstricke​

Fallstrick 1: Gemischte v2/v3-Abhängigkeiten​

Problem: Einige Abhängigkeiten verwenden Casbin v2, andere v3, was zu Konflikten führt.

Lösung: Der Build selbst ist unproblematisch: Das Go-Modulsystem behandelt v2 und v3 als separate Pakete, sodass beide in derselben Abhängigkeitsstruktur existieren können. Was Sie nicht tun können, ist, einen v3-Enforcer an eine Bibliothek zu übergeben, die einen v2-Enforcer erwartet. Halten Sie den Enforcer, seinen Adapter und seine Middleware auf derselben Major-Version.

Fallstrick 2: Adapter-Versionsinkompatibilität​

Problem: Verwendung eines v2-Adapters mit Casbin v3 (oder umgekehrt).

Lösung: Dies zeigt sich als Kompilierfehler, nicht als Überraschung zur Laufzeit. Prüfen Sie, welche Casbin-Major-Version die go.mod des Adapters erfordert, und verwenden Sie eine Release-Version, die zu Ihrem Enforcer passt.

Fallstrick 3: Vergessen interner Pakete​

Problem: Die Hauptanwendungs-Importe wurden aktualisiert, aber interne Pakete oder Tools wurden vergessen.

Lösung: Verwenden Sie go mod graph und go mod why, um alle Casbin-Abhängigkeiten zu finden:

go mod graph | grep casbin

Fallstrick 4: Kompilierungsprobleme bei benutzerdefinierten Adaptern​

Problem: Custom adapter won't compile after upgrade.

Solution: The adapter interface didn't change, so this suggests an import issue. Check that all Casbin imports in your adapter use v3:

import (
    "github.com/casbin/casbin/v3"
    "github.com/casbin/casbin/v3/persist"
)

FAQ​

Q: Is v2 still maintained?​

Zum Zeitpunkt dieses Textes erhält v2 kritische Fehlerbehebungen, aber neue Funktionen werden für v3 entwickelt. Planen Sie die Migration innerhalb der nächsten 6–12 Monate.

Q: Can I gradually migrate by having some services on v2 and others on v3?​

Ja! Sie können sogar dieselbe Policy-Datenbank nutzen. Dies ist einer der Vorteile der minimalen Änderungen in v3.

Q: Will my middleware (Gin, Echo, Fiber, etc.) work?​

Nur wenn es dieselbe Major Version wie Ihr Enforcer importiert. Prüfen Sie die go.mod des Middlewares; wenn es noch auf v2 basiert, rufen Sie Enforce() aus einem eigenen kleinen Handler auf, wie oben gezeigt.

Q: Do I need to update my .conf model files?​

Nein. Die Syntax der Model-Dateien ist unverändert.

Q: Do I need to update my .csv policy files?​

Nein. Das Format der Policy-Dateien ist unverändert.

Q: What about WatcherEx, FilteredAdapter, and other interfaces?​

Alle Interfaces bleiben unverändert. Wenn Ihr Code diese Interfaces implementiert, sind keine Änderungen nötig (außer den Import-Pfaden).

Q: Performance impact?​

Keiner. v3 nutzt dieselbe Evaluation Engine wie v2.

Q: Can I use v3 with Go 1.16?​

Prüfen Sie die go.mod im Casbin v3 Repository für die minimal unterstützte Go-Version. Generell wird die Verwendung der neuesten stabilen Go-Version empfohlen.

Viel Erfolg beim Upgrade!
