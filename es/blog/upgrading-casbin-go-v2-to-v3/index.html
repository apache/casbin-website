Actualizando **Casbin** (Go) de v2 a v3: Una Guía Completa de Migración

1 de febrero de 2026 · 9 min de lectura
Yang Luo
Creator of Casbin

Si estás ejecutando Casbin v2 en producción y te preguntas sobre la ruta de actualización a v3, esta guía es para ti. Cubriremos todo lo que necesitas saber sobre la transición, desde entender qué cambió hasta ejecutar una migración segura en producción.

¿Qué Cambió en v3?​

La buena noticia: v3 es principalmente un cambio de ruta de módulo con compatibilidad retroactiva completa. La lógica central de autorización, las APIs y la funcionalidad permanecen sin cambios. Esta fue una decisión intencional para minimizar la interrupción mientras seguimos las convenciones de versionado semántico de Go.

El Cambio Principal: Ruta del Módulo​

El único cambio disruptivo en v3 es la ruta del módulo de Go:

// v2
import "github.com/casbin/casbin/v2"

// v3
import "github.com/casbin/casbin/v3"

Eso es todo. Tus políticas existentes, modelos y lógica de código no necesitan cambiar. La migración es mecánica: actualiza las sentencias de importación y tu archivo go.mod.

¿Por qué Lanzar v3?​

Podrías preguntarte por qué lanzar una nueva versión mayor solo por un cambio de ruta de importación. La respuesta es el versionado semántico. El sistema de módulos de Go utiliza el número de versión mayor en la ruta de importación (/v2, /v3, etc.). Esto permite que múltiples versiones mayores coexistan en el mismo árbol de dependencias, lo cual es crucial para aplicaciones grandes con muchas dependencias.

Al lanzar v3, hemos:

  • Alineado con el versionado semántico de importaciones de Go
  • Habilitado la migración gradual en grafos de dependencias complejos
  • Preparado el terreno para mejoras futuras sin romper los usuarios existentes de v2

¿Qué Permaneció Igual?​

Todo lo demás. En serio.

  • Todas las APIs permanecen idénticas - Enforce(), AddPolicy(), GetAllRoles() y cualquier otro método funciona exactamente igual que antes
  • Sintaxis de modelo y política sin cambios - Tus archivos de modelo .conf y archivos de política .csv existentes funcionan sin modificación
  • Interfaz de adaptador sin cambios - Los métodos de persist.Adapter son los mismos; los adaptadores solo necesitan una compilación basada en la ruta del módulo v3
  • Características de rendimiento - Sin regresiones ni mejoras de rendimiento; es el mismo motor
  • Integraciones de middleware - El middleware funciona de la misma manera una vez que importa la misma versión mayor que tu enforcer

Nuevas Características en v3​

Desde el lanzamiento de v3.0.0 en diciembre de 2025, se han añadido varias nuevas características:

v3.7.0+: Integración Mejorada de Logger​

Ahora puedes integrar loggers personalizados en las operaciones centrales de enforcement y gestión de políticas de Casbin, proporcionando mejor observabilidad:

enforcer.SetLogger(yourCustomLogger)

v3.8.0+: API GetAllUsers()​

Una nueva API para distinguir usuarios de roles:

users, err := enforcer.GetAllUsers()

Esto es particularmente útil en sistemas RBAC donde necesitas listar usuarios reales separadamente de las definiciones de roles.

v3.9.0+: Detección de Ciclos Incorporada​

El enforcer ahora incluye detección automática de ciclos en jerarquías de roles, previniendo bucles infinitos:

// Automatically detects and prevents circular role assignments
enforcer.AddGroupingPolicy("alice", "admin")
enforcer.AddGroupingPolicy("admin", "alice") // Will be detected as a cycle

v3.10.0+: API Explain() para Insights de Autorización Impulsados por IA​

La última característica aprovecha las APIs de LLM para explicar decisiones de autorización en lenguaje natural:

enforcer.SetAIConfig(casbin.AIConfig{
    Endpoint: "https://api.openai.com/v1/chat/completions",
    APIKey:   os.Getenv("OPENAI_API_KEY"),
    Model:    "gpt-4",
})

explanation, err := enforcer.Explain("alice", "data1", "read")
// e.g. "Alice can read data1 because she has the 'reader' role..."

Esto es especialmente valioso para depurar políticas complejas y ayudar a partes interesadas no técnicas a entender las decisiones de autorización.

Estrategia de Migración​

Para Nuevos Proyectos​

Sencillo: simplemente usa v3 desde el principio.

go get github.com/casbin/casbin/v3
import "github.com/casbin/casbin/v3"

Para Proyectos Existentes en v2​

La migración implica tres pasos:

Paso 1: Actualiza tu go.mod​

go get github.com/casbin/casbin/v3
go mod tidy

Paso 2: Actualiza las Sentencias de Importación​

Busca y reemplaza todas las importaciones de Casbin en tu base de código:

# Using sed on Unix/Linux/Mac
find . -type f -name '*.go' -exec sed -i 's|github.com/casbin/casbin/v2|github.com/casbin/casbin/v3|g' {} +

# Or manually in your editor
# Find: github.com/casbin/casbin/v2
# Replace: github.com/casbin/casbin/v3

Paso 3: Actualiza las Importaciones del Adaptador (Si Aplica)​

Un adaptador implementa persist.Adapter de una versión principal específica, porque model.Model en casbin/v2 y casbin/v3 son tipos Go diferentes. Por lo tanto, un enforcer v3 necesita una versión del adaptador que importe github.com/casbin/casbin/v3. Revisa el go.mod del adaptador:

// Example: the PostgreSQL adapter already depends on casbin/v3
import pgadapter "github.com/apache/casbin-pg-adapter"

// The file adapter is built in and ships with each major version

Si tu adaptador aún no se ha actualizado, permanece en v2 para ese servicio hasta que lo haga, o abre un issue en el repositorio del adaptador.

Plan de Rollback​

Si necesitas hacer rollback:

  1. A nivel de código: Revierte los cambios de importación (usa control de versiones)
  2. A nivel de dependencias: go get github.com/casbin/casbin/v2@latest
  3. Despliegue: Usa tu proceso estándar de despliegue para revertir

Lo bueno de esta migración es que el rollback es trivial: simplemente revierte los cambios de importación y vuelve a desplegar.

¿Necesito Migrar Mi Base de Datos de Políticas?​

No. Tus datos de políticas existentes permanecen sin cambios. Las políticas se almacenan como cadenas simples (sujeto, objeto, acción, etc.) y no tienen dependencia con la versión de Casbin.

Pruebas de Tu Migración​

Pruebas Automatizadas​

Tus pruebas existentes deberían pasar sin modificaciones:

func TestPolicyEnforcement(t *testing.T) {
    // This test works identically in v2 and v3
    e, _ := casbin.NewEnforcer("model.conf", "policy.csv")
    
    ok, _ := e.Enforce("alice", "data1", "read")
    if !ok {
        t.Error("Expected alice to have read access to data1")
    }
}

Pruebas de Integración​

El middleware que toma un *casbin.Enforcer está vinculado a una versión principal de la misma manera que los adaptadores. Si tu middleware aún importa casbin/v2, llamar al enforcer directamente requiere unas pocas líneas:

// Example with Gin
import (
    "net/http"

    "github.com/casbin/casbin/v3"
    "github.com/gin-gonic/gin"
)

func Authorizer(e *casbin.Enforcer) gin.HandlerFunc {
    return func(c *gin.Context) {
        ok, err := e.Enforce(c.GetString("user"), c.Request.URL.Path, c.Request.Method)
        if err != nil || !ok {
            c.AbortWithStatus(http.StatusForbidden)
            return
        }
        c.Next()
    }
}

Pruebas de Carga​

Ejecuta tus pruebas de carga estándar contra la compilación v3. Las características de rendimiento deberían ser idénticas a v2.

Verificación de Políticas​

Compara la evaluación de políticas entre versiones:

# Export policies from v2
# Load into v3
# Run test cases against both
# Compare results

Si ves alguna diferencia, es probable que sea un bug; ¡por favor repórtalo!

Errores Comunes​

Error 1: Dependencias Mixtas v2/v3​

Problema: Algunas dependencias usan Casbin v2, otras usan v3, causando conflictos.

Solución: La compilación en sí está bien: el sistema de módulos de Go trata v2 y v3 como paquetes separados, por lo que ambos pueden coexistir en el mismo árbol de dependencias. Lo que no puedes hacer es pasar un enforcer v3 a una biblioteca que espera uno v2. Mantén el enforcer, su adaptador y su middleware en la misma versión principal.

Error 2: Desajuste de Versión del Adaptador​

Problema: Usar un adaptador v2 con Casbin v3 (o viceversa).

Solución: Esto aparece como un error de compilación, no como una sorpresa en tiempo de ejecución. Verifica qué versión principal de Casbin requiere el go.mod del adaptador y usa una versión que coincida con tu enforcer.

Error 3: Olvidar Paquetes Internos​

Problema: Se actualizaron las importaciones de la aplicación principal pero se olvidaron los paquetes internos o herramientas.

Solución: Usa go mod graph y go mod why para encontrar todas las dependencias de Casbin:

go mod graph | grep casbin

Error 4: Problemas de Compilación de Adaptadores Personalizados​

Problema: El adaptador personalizado no se compila después de la actualización.

Solución: La interfaz del adaptador no cambió, por lo que esto sugiere un problema de importación. Verifique que todas las importaciones de Casbin en su adaptador utilicen v3:

import (
    "github.com/casbin/casbin/v3"
    "github.com/casbin/casbin/v3/persist"
)

Preguntas frecuentes​

P: ¿v2 sigue siendo mantenido?​

En el momento de escribir este documento, v2 recibe correcciones críticas de errores, pero las nuevas funcionalidades se desarrollan para v3. Planifique migrar dentro de los próximos 6-12 meses.

P: ¿Puedo migrar gradualmente teniendo algunos servicios en v2 y otros en v3?​

¡Sí! Incluso pueden compartir la misma base de datos de políticas. Esta es una de las ventajas de los cambios mínimos en v3.

P: ¿Funcionará mi middleware (Gin, Echo, Fiber, etc.)?​

Solo si importa la misma versión principal que su enforcer. Revise el go.mod del middleware; si aún está en v2, llame a Enforce() desde un pequeño handler propio como se muestra arriba.

P: ¿Necesito actualizar mis archivos de modelo .conf?​

No. La sintaxis del archivo de modelo no ha cambiado.

P: ¿Necesito actualizar mis archivos de política .csv?​

No. El formato del archivo de política no ha cambiado.

P: ¿Qué pasa con WatcherEx, FilteredAdapter y otras interfaces?​

Todas las interfaces permanecen sin cambios. Si su código implementa estas interfaces, no se necesitan modificaciones (más allá de las rutas de importación).

P: ¿Impacto en el rendimiento?​

Ninguno. v3 utiliza el mismo motor de evaluación que v2.

P: ¿Puedo usar v3 con Go 1.16?​

Revise el go.mod en el repositorio de Casbin v3 para conocer la versión mínima de Go compatible. Generalmente, se recomienda utilizar la última versión estable de Go.

¡Feliz actualización!

Términos de Servicio

Apache Casbin (Incubating) es un esfuerzo en proceso de incubación en The Apache Software Foundation (ASF), patrocinado por Apache Incubator. La incubación es obligatoria para todos los proyectos recién aceptados hasta que una revisión adicional indique que la infraestructura, las comunicaciones y el proceso de toma de decisiones se han estabilizado de manera consistente con otros proyectos exitosos de ASF. Si bien el estado de incubación no refleja necesariamente la completitud o estabilidad del código, indica que el proyecto aún no ha sido plenamente respaldado por ASF.
