**Sintaxis del Modelo**

Cada archivo CONF de modelo debe definir estas cuatro secciones: [request_definition], [policy_definition], [policy_effect] y [matchers].

  • Para RBAC, agregue una sección [role_definition].
  • Para RBAC con constraints (p. ej., separación de funciones), puede agregar [constraint_definition].
  • Las líneas que comienzan con # son comentarios; el resto de la línea se ignora.

Request Definition​

La sección [request_definition] define los parámetros pasados a e.Enforce(...).

[request_definition]
r = sub, obj, act

Aquí sub, obj y act son la tripleta estándar: subject, object y action. Puede cambiar el formato, p. ej. sub, act cuando no hay recurso, o sub, sub2, obj, act cuando intervienen dos subjects.

Policy Definition​

La sección [policy_definition] describe la estructura de las reglas de política. Por ejemplo:

[policy_definition]
p = sub, obj, act
p2 = sub, act

Con un archivo de políticas como:

p, alice, data1, read
p2, bob, write-all-objects

Cada línea en el archivo de políticas es una regla. El primer token es el tipo de política (p, p2, etc.) y debe coincidir con una definición de política. El ejemplo anterior produce estos bindings para el matcher:

(alice, data1, read) -> (p.sub, p.obj, p.act)
(bob, write-all-objects) -> (p2.sub, p2.act)
consejo

Los elementos de las reglas de política siempre se tratan como strings. Consulte casbin/casbin#113 para ver la discusión.

Policy Effect​

La sección [policy_effect] define cómo combinar los resultados cuando múltiples políticas coinciden (p. ej., una permite, otra deniega).

[policy_effect]
e = some(where (p.eft == allow))

Esto da lugar a allow-override: si alguna política coincidente tiene effect allow, el resultado es allow. El campo p.eft es el effect de la política (allow o deny). Es opcional y su valor predeterminado es allow cuando se omite.

Aquí hay un policy effect alternativo:

[policy_effect]
e = !some(where (p.eft == deny))

Esto implementa deny-override: el resultado es allow solo cuando ninguna política coincidente tiene effect deny. Puede combinar expresiones con operadores lógicos:

[policy_effect]
e = some(where (p.eft == allow)) && !some(where (p.eft == deny))

Esa expresión requiere al menos un allow y ningún deny. Casbin soporta tanto allow como deny; cuando ambos coinciden, deny gana.

nota

El policy effect debe ser uno de los effects integrados siguientes. Las expresiones de effect personalizadas no están soportadas en la implementación actual.

Policy effects integrados disponibles:

Policy EffectSignificadoEjemplo
some(where (p.eft == allow))allow-overrideACL, RBAC, etc.
!some(where (p.eft == deny))deny-overrideDeny-override
some(where (p.eft == allow)) && !some(where (p.eft == deny))allow-and-denyAllow-and-deny
priority(p.eft) || denypriorityPriority
subjectPriority(p.eft)priority based on roleSubject-Priority

Constraint Definition​

La sección opcional [constraint_definition] define invariantes para RBAC (p. ej., separación de funciones). Los constraints se verifican cuando cambian las asignaciones de roles. Debe tener [role_definition] para usar constraints.

[constraint_definition]
c = sod("finance_requester", "finance_approver")
c2 = sodMax(["payroll_view", "payroll_edit", "payroll_approve"], 1)
c3 = roleMax("superadmin", 2)
c4 = rolePre("db_admin", "security_trained")

Constraint Types​

Separation of Duties (sod) — Un usuario no puede tener ambos roles. Si Alice tiene finance_requester, no se le puede asignar finance_approver.

c = sod("finance_requester", "finance_approver")

Separation of Duties Max (sodMax) — Limita cuántos roles de un conjunto puede tener un usuario. Con sodMax(..., 1) para roles de nómina, un usuario puede tener como máximo uno de view, edit o approve.

c2 = sodMax(["payroll_view", "payroll_edit", "payroll_approve"], 1)

Role Cardinality (roleMax) — Establece un tope de cuántos usuarios pueden tener un rol. Por ejemplo, como máximo dos usuarios pueden tener superadmin.

c3 = roleMax("superadmin", 2)

Prerequisite Role (rolePre) — Se requiere un rol antes que otro. Por ejemplo, un usuario debe tener security_trained antes de ser asignado a db_admin.

c4 = rolePre("db_admin", "security_trained")

How Constraints Work​

Los constraints se aplican cuando cambian las grouping policies (p. ej., AddGroupingPolicy(), RemoveGroupingPolicy()). Si un cambio violaría un constraint, la operación falla con un error y la política no se actualiza.

Cuando se carga el modelo, todos los constraints se verifican contra las políticas actuales. Los constraints inválidos (sintaxis incorrecta, falta de configuración RBAC o datos actuales que ya violan un constraint) hacen que la carga falle con un error claro.

Matchers​

La sección [matchers] define cómo se evalúan las solicitudes frente a las reglas de política.

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act

Este matcher requiere que el sujeto, objeto y acción de la solicitud coincidan exactamente con los campos de la política.

Los matchers admiten operadores aritméticos (+, -, *, /) y lógicos (&&, ||, !).

Orden de expresiones en Matchers​

El orden de las expresiones en un matcher puede afectar significativamente el rendimiento. Ejemplo:

const rbac_models = `
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
`

func TestManyRoles(t *testing.T) {

    m, _ := model.NewModelFromString(rbac_models)
    e, _ := NewEnforcer(m, false)

    roles := []string{"admin", "manager", "developer", "tester"}

    // 2500 projects
    for nbPrj := 1; nbPrj < 2500; nbPrj++ {
        // 4 objects and 1 role per object (so 4 roles)
        for _, role := range roles {
            roleDB := fmt.Sprintf("%s_project:%d", role, nbPrj)
            objectDB := fmt.Sprintf("/projects/%d", nbPrj)
            e.AddPolicy(roleDB, objectDB, "GET")
        }
        jasmineRole := fmt.Sprintf("%s_project:%d", roles[1], nbPrj)
        e.AddGroupingPolicy("jasmine", jasmineRole)
    }

    e.AddGroupingPolicy("abu", "manager_project:1")
    e.AddGroupingPolicy("abu", "manager_project:2499")

    // With same number of policies
    // User 'abu' has only two roles
    // User 'jasmine' has many roles (1 role per policy, here 2500 roles)

    request := func(subject, object, action string) {
        t0 := time.Now()
        resp, _ := e.Enforce(subject, object, action)
        tElapse := time.Since(t0)
        t.Logf("RESPONSE %-10s %s\t %s : %5v IN: %+v", subject, object, action, resp, tElapse)
        if tElapse > time.Millisecond*100 {
            t.Errorf("More than 100 milliseconds for %s %s %s : %+v", subject, object, action, tElapse)
        }
    }

    request("abu", "/projects/1", "GET")        // really fast because only 2 roles in all policies and at the beginning of the casbin_rule table
    request("abu", "/projects/2499", "GET")     // fast because only 2 roles in all policies
    request("jasmine", "/projects/1", "GET")    // really fast at the beginning of the casbin_rule table

    request("jasmine", "/projects/2499", "GET") // slow and fails the only 1st time   <<<< pb here
    request("jasmine", "/projects/2499", "GET") // fast maybe due to internal cache mechanism

    // same issue with non-existing roles
    // request("jasmine", "/projects/999999", "GET") // slow fails the only 1st time   <<<< pb here
    // request("jasmine", "/projects/999999", "GET") // fast maybe due to internal cache mechanism
}

Múltiples tipos de sección​

Puede definir múltiples secciones de request, policy, effect o matcher con sufijos como r2, p2, e2, m2. Se emparejan por sufijo: r2 coincide con p2 mediante m2 y se combina con e2.

Para usar un conjunto no predeterminado, pase un EnforceContext como primer argumento a enforce. Estructura:

EnforceContext{"r2","p2","e2","m2"}
type EnforceContext struct {
    RType string
    PType string
    EType string
    MType string
}
const enforceContext = new EnforceContext('r2', 'p2', 'e2', 'm2');
class EnforceContext {
  constructor(rType, pType, eType, mType) {
    this.pType = pType;
    this.eType = eType;
    this.mType = mType;
    this.rType = rType;
  }
}
EnforceContext enforceContext = new EnforceContext("2");
public class EnforceContext {
    private String pType;
    private String eType;
    private String mType;
    private String rType;
    public EnforceContext(String suffix) {
      this.pType = "p" + suffix;
      this.eType = "e" + suffix;
      this.mType = "m" + suffix;
      this.rType = "r" + suffix;
    }
}

Ejemplo de uso (consulte los ejemplos de model y policy):

// Pass in a suffix as a parameter to NewEnforceContext, such as 2 or 3, and it will create r2, p2, etc.
enforceContext := NewEnforceContext("2")
// You can also specify a certain type individually
enforceContext.EType = "e"
// Don't pass in EnforceContext; the default is r, p, e, m
e.Enforce("alice", "data2", "read")        // true
// Pass in EnforceContext
e.Enforce(enforceContext, struct{ Age int }{Age: 70}, "/data1", "read")        //false
e.Enforce(enforceContext, struct{ Age int }{Age: 30}, "/data1", "read")        //true
// Pass in a suffix as a parameter to NewEnforceContext, such as 2 or 3, and it will create r2, p2, etc.
const enforceContext = new NewEnforceContext('2');

// You can also specify a certain type individually
enforceContext.eType = "e"

// Don't pass in EnforceContext; the default is r, p, e, m
e.Enforce("alice", "data2", "read")        // true

// Pass in EnforceContext
e.Enforce(enforceContext, {Age: 70}, "/data1", "read")        //false
e.Enforce(enforceContext, {Age: 30}, "/data1", "read")        //true
// Pass in a suffix as a parameter to NewEnforceContext, such as 2 or 3, and it will create r2, p2, etc.
EnforceContext enforceContext = new EnforceContext("2");
// You can also specify a certain type individually
enforceContext.seteType("e");
// Don't pass in EnforceContext; the default is r, p, e, m
e.enforce("alice", "data2", "read");  // true
// Pass in EnforceContext
// TestEvalRule is located in https://github.com/apache/casbin-jcasbin/blob/master/src/test/java/org/casbin/jcasbin/main/AbacAPIUnitTest.java#L56
e.enforce(enforceContext, new AbacAPIUnitTest.TestEvalRule("alice", 70), "/data1", "read"); // false
e.enforce(enforceContext, new AbacAPIUnitTest.TestEvalRule("alice", 30), "/data1", "read"); // true

Gramática especial: operador in​

El operador in verifica si la matriz del lado derecho contiene el valor del lado izquierdo (usando igualdad ==, sin coerción de tipos). El lado izquierdo puede ser cualquier valor; el lado derecho debe ser una matriz del mismo tipo. En Go, las matrices deben ser []interface{}.

Ejemplos de referencia: rbac_model_matcher_using_in_op, keyget2_model y keyget_model.

Ejemplo:

[request_definition]
r = sub, obj
...
[matchers]
m = r.sub.Name in (r.obj.Admins)
e.Enforce(Sub{Name: "alice"}, Obj{Name: "a book", Admins: []interface{}{"alice", "bob"}})

Evaluadores de expresiones​

Los matchers son evaluados por un motor de expresiones específico del lenguaje. Casbin los utiliza para proporcionar una sintaxis PERM unificada. Algunos motores admiten características adicionales más allá de la sintaxis documentada; esas características pueden no estar disponibles en otros lenguajes. Use solo la sintaxis documentada si necesita compatibilidad entre lenguajes.

Apache Casbin (Incubating) es un esfuerzo en proceso de incubación en The Apache Software Foundation (ASF), patrocinado por Apache Incubator. La incubación es obligatoria para todos los proyectos recién aceptados hasta que una revisión adicional indique que la infraestructura, las comunicaciones y el proceso de toma de decisiones se han estabilizado de manera consistente con otros proyectos exitosos de ASF. Si bien el estado de incubación no refleja necesariamente la completitud o estabilidad del código, indica que el proyecto aún no ha sido plenamente respaldado por ASF.
