Kubernetes Admission Webhook

Visión General​

Casbin K8s-Gatekeeper es un webhook de admisión de Kubernetes que utiliza Casbin para la autorización. Define modelos y políticas de forma declarativa para permitir o denegar operaciones sobre cualquier recurso de Kubernetes, sin necesidad de código personalizado en el webhook. Mantenido por la comunidad de Casbin: github.com/apache/casbin-k8s-gatekeeper.

Ejemplo básico​

Ejemplo: denegar despliegues que utilicen imágenes con una etiqueta específica, usando solo configuración:

Modelo:

[request_definition]
r =  obj

[policy_definition]
p =  obj,eft

[policy_effect]
e = !some(where (p.eft == deny))

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
contain(split(accessWithWildcard(${OBJECT}.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj)

Política:

p, "1.14.1",deny

Esto utiliza el lenguaje ACL estándar de Casbin, que debería ser sencillo si has leído los capítulos introductorios.

Casbin K8s-Gatekeeper ofrece varias ventajas:

  • Fácil de usar: escribe configuraciones ACL en lugar de mucho código
  • Admite actualizaciones de configuración en vivo sin reiniciar el plugin
  • Flexible: aplica reglas arbitrarias a cualquier recurso de Kubernetes usando kubectl gatekeeper
  • Simplifica la implementación de webhooks de admisión de Kubernetes: no necesitas entender los internos del webhook ni escribir código de webhook. Solo define restricciones y escribe ACL de Casbin.
  • Mantenido por la comunidad: contáctanos con preguntas o problemas

1.1 Cómo funciona Casbin K8s-Gatekeeper​

K8s-Gatekeeper es un webhook de admisión para Kubernetes que utiliza Casbin para aplicar reglas de control de acceso personalizadas, evitando operaciones no deseadas sobre recursos de Kubernetes.

Casbin es una biblioteca eficiente de control de acceso de código abierto que admite diversos modelos de autorización. Para más detalles, consulta la Visión general.

Los webhooks de admisión en Kubernetes son devoluciones de llamada HTTP que reciben y procesan solicitudes de admisión. K8s-Gatekeeper es un ValidatingAdmissionWebhook que acepta o rechaza solicitudes de admisión. Las solicitudes de admisión son peticiones HTTP que describen operaciones sobre recursos de Kubernetes (por ejemplo, crear o eliminar un despliegue). Para más información, consulta la documentación de Kubernetes.

1.2 Flujo de trabajo de ejemplo​

Cuando alguien crea un despliegue con un pod nginx (mediante kubectl o clientes de Kubernetes), Kubernetes genera una solicitud de admisión como esta (en formato YAML):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  selector:
    matchLabels:
      app: nginx
  replicas: 1
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.1
        ports:
        - containerPort: 80

Esta solicitud pasa por varias capas de middleware, incluyendo K8s-Gatekeeper. K8s-Gatekeeper detecta todos los aplicadores (enforcers) de Casbin almacenados en etcd de Kubernetes (creados y mantenidos por los usuarios mediante kubectl o el cliente Go proporcionado). Cada aplicador contiene un modelo y una política de Casbin. La solicitud de admisión se evalúa secuencialmente por cada aplicador y debe pasar todos los aplicadores para ser aceptada.

(Si no estás familiarizado con los aplicadores, modelos o políticas de Casbin, consulta Primeros pasos).

Por ejemplo, si un administrador desea bloquear la imagen 'nginx:1.14.1' mientras permite 'nginx:1.3.1', puede crear un aplicador con este modelo y política (los detalles de creación y configuración siguen en las secciones posteriores):

Modelo:

[request_definition]
r =  obj

[policy_definition]
p =  obj,eft

[policy_effect]
e = !some(where (p.eft == deny))

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") == p.obj

Política:

p, "nginx:1.13.1",allow
p, "nginx:1.14.1",deny

Crear un aplicador con este modelo y política rechazará la solicitud de admisión, impidiendo que Kubernetes cree el despliegue.

2. Instalando K8s-gatekeeper​

Hay tres métodos de instalación disponibles: Webhook externo, Webhook interno y Helm.

nota

Estos métodos de instalación son solo para fines de evaluación. Para implementaciones en producción, revisa el Capítulo 5. Configuraciones avanzadas y aplica las modificaciones de seguridad necesarias antes de instalar.

2.1 Webhook interno​

2.1.1 Paso 1: Compilar la imagen​

Para la implementación de webhook interno, K8s-gatekeeper se ejecuta como un servicio de Kubernetes. Compila la imagen:

docker build --target webhook -t k8s-gatekeeper .

Esto crea una imagen local llamada 'k8s-gatekeeper:latest'.

nota

Para usuarios de minikube, ejecuta eval $(minikube -p minikube docker-env) antes de 'docker build'.

2.1.2 Paso 2: Desplegar servicios y recursos​

Ejecute estos comandos:

kubectl apply -f config/rbac.yaml
kubectl apply -f config/webhook_deployment.yaml 
kubectl apply -f config/webhook_internal.yaml

Verifique el despliegue con kubectl get pods.

2.1.3 Paso 3: Instalar recursos CRD​

Instale las definiciones de recursos personalizados:

kubectl apply -f config/auth.casbin.org_casbinmodels.yaml 
kubectl apply -f config/auth.casbin.org_casbinpolicies.yaml

2.2 Webhook externo​

Para el despliegue de webhook externo, K8s-gatekeeper se ejecuta fuera de Kubernetes. Kubernetes requiere HTTPS para los webhooks de admisión. Proporcionamos certificados de prueba y una clave privada (no seguros para producción). Para certificados personalizados, consulte Capítulo 5. Configuraciones avanzadas.

El certificado proporcionado está emitido para 'webhook.domain.local'. Actualice su archivo hosts (por ejemplo, /etc/hosts) para que 'webhook.domain.local' apunte a la dirección IP donde se ejecuta K8s-gatekeeper.

Ejecute:

go mod tidy
go mod vendor
go run cmd/webhook/main.go
kubectl apply -f config/auth.casbin.org_casbinmodels.yaml 
kubectl apply -f config/auth.casbin.org_casbinpolicies.yaml
kubectl apply -f config/webhook_external.yaml

2.3 Instalación mediante Helm​

2.3.1 Paso 1: Construir la imagen​

Consulte Capítulo 2.1.1.

2.3.2 Instalación de Helm​

Ejecute: helm install k8sgatekeeper ./k8sgatekeeper

3. Uso de K8s-gatekeeper​

3.1 Creación de modelos y políticas de Casbin​

Cree modelos y políticas utilizando kubectl o el cliente Go proporcionado.

3.1.1 Crear/Actualizar mediante kubectl​

En K8s-gatekeeper, los modelos de Casbin se almacenan como recursos CRD 'CasbinModel'. La definición se encuentra en config/auth.casbin.org_casbinmodels.yaml.

Vea ejemplos en example/allowed_repo/model.yaml. Campos importantes:

  • metadata.name: Nombre del modelo. Debe coincidir con el nombre del objeto CasbinPolicy asociado para que K8s-gatekeeper los empareje correctamente.
  • spec.enable: Establezca en "false" para deshabilitar este modelo y su política asociada.
  • spec.modelText: Cadena que contiene la definición del modelo de Casbin.

Las políticas de Casbin se almacenan como recursos CRD 'CasbinPolicy', definidos en config/auth.casbin.org_casbinpolicies.yaml.

Vea ejemplos en example/allowed_repo/policy.yaml. Campos importantes:

  • metadata.name: Nombre de la política. Debe coincidir con el nombre del objeto CasbinModel asociado.
  • spec.policyItem: Cadena que contiene la definición de la política de Casbin.

Aplique sus archivos CasbinModel y CasbinPolicy:

kubectl apply -f <filename>

K8s-gatekeeper detecta nuevos pares CasbinModel/CasbinPolicy en un plazo de 5 segundos.

3.1.2 Crear/Actualizar mediante el cliente Go​

Para escenarios donde el acceso directo por shell a los nodos del clúster no es práctico (por ejemplo, al construir plataformas cloud automatizadas), proporcionamos un cliente Go para gestionar recursos CasbinModel y CasbinPolicy.

La biblioteca del cliente Go se encuentra en pkg/client.

En client.go, utilice esta función para crear un cliente:

func NewK8sGateKeeperClient(externalClient bool) (*K8sGateKeeperClient, error)

El parámetro externalClient indica si K8s-gatekeeper se ejecuta dentro o fuera del clúster de Kubernetes.

En model.go, se proporcionan funciones para crear, eliminar y modificar CasbinModel. Consulte model_test.go para ver ejemplos de uso.

En policy.go, se proporcionan funciones para crear, eliminar y modificar CasbinPolicy. Consulte policy_test.go para ver ejemplos de uso.

3.1.2 Pruebas de K8s-gatekeeper​

Después de crear el modelo y la política desde example/allowed_repo, pruebe con:

kubectl apply -f example/allowed_repo/testcase/reject_1.yaml

Kubernetes debería rechazar esta solicitud, citando el webhook como motivo del rechazo. Sin embargo, aplicar example/allowed_repo/testcase/approve_2.yaml debería tener éxito.

4. Escritura de modelos y políticas para K8s-gatekeeper​

Ensure you understand Casbin model and policy syntax before proceeding. If not, read the Get Started section first. This chapter assumes familiarity with Casbin models and policies.

4.1 Definición de la solicitud​

When K8s-gatekeeper evaluates a request, the input is always an AdmissionReview Go object. The enforcer is used as follows:

ok, err := enforcer.Enforce(admission)

donde admission es un objeto AdmissionReview de la API oficial de Go de Kubernetes "k8s.io/api/admission/v1". La definición de la estructura está disponible en: https://github.com/kubernetes/api/blob/master/admission/v1/types.go. Documentación adicional: https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#webhook-request-and-response.

Para los modelos de K8s-gatekeeper, el request_definition debe seguir siempre este formato:

    [request_definition]
    r =  obj

El nombre 'obj' puede cambiarse siempre que se utilice de forma consistente en la sección [matchers].

4.2 Matchers del Modelo​

Utilice la función ABAC de Casbin para escribir reglas. Sin embargo, el evaluador de expresiones de Casbin no admite de forma nativa la indexación de mapas/arrays ni la expansión de arrays. K8s-gatekeeper proporciona funciones de extensión para abordar esto. Si necesita funcionalidad adicional, abra un issue o envíe una pull request.

For background on Casbin functions, see Function.

Funciones de extensión:

4.2.1 Funciones de Extensión​

4.2.1.1 access​

La función access permite la indexación de mapas y arrays. Consulte example/allowed_repo/model.yaml:

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") == p.obj

Aquí, access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") es equivalente a r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Image, donde r.obj.Request.Object.Object.Spec.Template.Spec.Containers es un slice.

access también puede llamar a funciones sin parámetros que devuelven un único valor. Consulte example/container_resource_limit/model.yaml:

[matchers]
  m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
  parseFloat(access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","cpu","Value")) >= parseFloat(p.cpu) && \
  parseFloat(access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","memory","Value")) >= parseFloat(p.memory)

Aquí, access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","cpu","Value") equivale a r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Resources.Limits["cpu"].Value(), donde r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Resources.Limits es un mapa y Value() es una función sin parámetros que devuelve un único valor.

4.2.1.2 accessWithWildcard​

Para comprobar condiciones en todos los elementos de un array (por ejemplo, "todos los elementos deben comenzar por 'aaa'") sin bucles for, utilice accessWithWildcard con expansión de mapas/slices.

Si a.b.c es el array [aaa,bbb,ccc,ddd,eee], entonces accessWithWildcard(a,"b","c","*") devuelve el slice [aaa,bbb,ccc,ddd,eee]. El comodín * expande el slice.

Se admiten múltiples comodines. Por ejemplo, accessWithWildcard(a,"b","c","*","*") devuelve [a.b.c[0][0], a.b.c[0][1], ..., a.b.c[1][0], a.b.c[1][1], ...].

4.2.1.3 Funciones con Argumentos de Longitud Variable​

El evaluador de expresiones de Casbin expande automáticamente los arrays como argumentos de longitud variable. Aprovechando esto para la expansión de arrays/slices/mapas, varias funciones aceptan arrays/slices:

  • contain(): Acepta múltiples parámetros y devuelve si algún parámetro (excepto el último) es igual al último parámetro.
  • split(a,b,c...,sep,index): Devuelve [splits(a,sep)[index], splits(b,sep)[index], splits(c,sep)[index], ...].
  • len(): Devuelve el número de argumentos de longitud variable.
  • matchRegex(a,b,c...,regex): Devuelve si todos los parámetros (a, b, c, ...) coinciden con la expresión regular.

Ejemplo de example/disallowed_tag/model.yaml:

    [matchers]
    m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
    contain(split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj)

Si accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image") devuelve ["a:b", "c:d", "e:f", "g:h"], la operación split procesa cada elemento con soporte para argumentos de longitud variable, seleccionando el índice 1 de cada uno. Así, split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) devuelve ["b","d","f","h"]. Finalmente, contain(split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj) comprueba si p.obj existe en ["b","d","f","h"].

4.2.1.2 Funciones de Conversión de Tipos​

  • ParseFloat(): Convierte enteros a flotantes (requerido porque las comparaciones necesitan tipo float).
  • ToString(): Convierte objetos a cadenas. El objeto debe tener un tipo subyacente de cadena (por ejemplo, type XXX string).
  • IsNil(): Devuelve si el parámetro es nil.

5. Configuración Avanzada​

5.1 Configuración de Certificados​

Kubernetes requiere que los webhooks utilicen HTTPS. Hay dos opciones disponibles:

  • Certificados autofirmados (utilizados en los ejemplos de este repositorio)
  • Certificados públicos confiables

5.1.1 Certificados Autofirmados​

Los certificados autofirmados utilizan una Autoridad de Certificación (CA) que no es reconocida públicamente. Debe configurar Kubernetes para confiar en esta CA.

Los ejemplos del repositorio utilizan una CA personalizada con clave privada y certificado almacenados en config/certificate/ca.key y config/certificate/ca.crt. El certificado del webhook config/certificate/server.crt es emitido por esta CA para los dominios "webhook.domain.local" (webhook externo) y "casbin-webhook-svc.default.svc" (webhook interno).

La información de la CA se pasa a Kubernetes mediante archivos de configuración de webhook. Tanto config/webhook_external.yaml como config/webhook_internal.yaml contienen un campo "CABundle" con el certificado de la CA codificado en base64.

Para cambiar el certificado/dominio (por ejemplo, mover el webhook a otro namespace o cambiar los dominios):

  1. Generar una nueva CA:

    • Generar la clave privada de la CA:

      openssl genrsa -des3 -out ca.key 2048

    • Eliminar la protección por contraseña:

      openssl rsa -in ca.key -out ca.key

  2. Generar la clave privada del servidor webhook:

    openssl genrsa -des3 -out server.key 2048
    openssl rsa -in server.key -out server.key

  3. Firmar el certificado del webhook con la CA:

    • Copie el archivo de configuración OpenSSL de su sistema (búsquelo con openssl version -a, normalmente openssl.cnf).

    • Modifique el archivo de configuración:

      • En la sección [req], agregue: req_extensions = v3_req

      • En la sección [v3_req], agregue: subjectAltName = @alt_names

      • Añada al final:

        [alt_names]
        DNS.2=<Your desired domain>

        Nota: Reemplace 'casbin-webhook-svc.default.svc' con el nombre real de su servicio si lo ha modificado.

    • Genere una solicitud de certificado:

      openssl req -new -nodes -keyout server.key -out server.csr -config openssl.cnf

    • Firme el certificado con la CA:

      openssl x509 -req -days 3650 -in server.csr -out server.crt -CA ca.crt -CAkey ca.key -CAcreateserial -extensions v3_req -extensions SAN -extfile openssl.cnf

  4. Actualice el campo 'CABundle' tanto en config/webhook_external.yaml como en config/webhook_internal.yaml con el nuevo certificado de la CA codificado en base64.

  5. Para implementaciones con Helm, aplique los cambios equivalentes en los charts de Helm.

5.1.2 Publicly Trusted Certificates​

Con certificados públicos de confianza, omita los procedimientos anteriores. Elimine el campo "CABundle" de config/webhook_external.yaml y config/webhook_internal.yaml, y configure el dominio para que sea su dominio registrado.

Si bien el estado de incubación no refleja necesariamente la completitud o estabilidad del código, indica que el proyecto aún no ha sido plenamente respaldado por ASF.
