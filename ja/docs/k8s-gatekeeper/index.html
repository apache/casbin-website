Kubernetes Admission Webhook

概要​

Casbin K8s-Gatekeeper は、Casbinを認可に使用しているKubernetes admission webhookです。任意のKubernetesリソースに対する操作を許可または拒否するために、モデルとポリシーを宣言的に定義します。Webhook内でのカスタムコードは不要です。Casbinコミュニティによってメンテナンスされています: github.com/apache/casbin-k8s-gatekeeper.

基本的な例​

例: 特定のタグを持つイメージを使用するデプロイメントを、設定のみで拒否します:

Model:

[request_definition]
r =  obj

[policy_definition]
p =  obj,eft

[policy_effect]
e = !some(where (p.eft == deny))

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
contain(split(accessWithWildcard(${OBJECT}.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj)

Policy:

p, "1.14.1",deny

これは標準的なCasbin ACL言語を使用しており、入門編を読んだ方であれば理解しやすいはずです。

Casbin K8s-Gatekeeperにはいくつかの利点があります:

  • 使いやすい— extensiveなコードの代わりにACL設定を記述します
  • プラグインの再起動なしでライブ設定更新をサポートします
  • 柔軟性— kubectl gatekeeper を使用して任意のルールを任意のKubernetesリソースに適用できます
  • Kubernetes admission webhookの実装を簡素化します—webhookの内部構造を理解したり、webhookコードを書いたりする必要はありません。制約を定義し、Casbin ACLを書くだけです。
  • コミュニティによるメンテナンス—質問や問題についてはご連絡ください

1.1 Casbin K8s-Gatekeeperの仕組み​

K8s-Gatekeeperは、Casbin を使用してカスタムのアクセス制御ルールを強制し、Kubernetesリソースに対する望ましくない操作を防ぐKubernetes用のadmission webhookです。

Casbinは、さまざまな認可モデルをサポートする効率的なオープンソースのアクセス制御ライブラリです。詳細については、Overview を参照してください。

Kubernetesのadmission webhookは、admissionリクエストを受信および処理するHTTPコールバックです。K8s-Gatekeeperは、admissionリクエストを受け入れるか拒否するかを決めるValidatingAdmissionWebhookです。Admissionリクエストとは、Kubernetesリソースに対する操作（例えば、デプロイメントの作成や削除）を記述したHTTPリクエストです。詳細については、Kubernetes documentation を参照してください。

1.2 ワークフローの例​

誰かがnginxポッドを含むデプロイメントを作成した場合（kubectlまたはKubernetesクライアント経由）、Kubernetesは以下のようなadmissionリクエストを生成します（YAML形式）:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  selector:
    matchLabels:
      app: nginx
  replicas: 1
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.1
        ports:
        - containerPort: 80

このリクエストは、K8s-Gatekeeperを含むミドルウェア層を通過します。K8s-Gatekeeperは、Kubernetes etcdに格納されているすべてのCasbinエンフォーサーを検出します（ユーザーが kubectl または提供されたGoクライアントを通じて作成・管理）。各エンフォーサーにはCasbinモデルとポリシーが含まれています。Admissionリクエストは各エンフォーサーによって順次評価され、すべてのエンフォーサーを通過する必要があります。

(Casbinのエンフォーサー、モデル、またはポリシーに不熟悉な場合は、Get Started を参照してください)。

例えば、管理者が 'nginx:1.14.1' イメージをブロックしつつ 'nginx:1.3.1' を許可したい場合、以下のモデルとポリシーを持つエンフォーサーを作成できます（作成と設定の詳細は後続のセクションに記載されています）:

Model:

[request_definition]
r =  obj

[policy_definition]
p =  obj,eft

[policy_effect]
e = !some(where (p.eft == deny))

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") == p.obj

Policy:

p, "nginx:1.13.1",allow
p, "nginx:1.14.1",deny

このモデルとポリシーでエンフォーサーを作成すると、admissionリクエストが拒否され、Kubernetesによるデプロイメントの作成が防止されます。

2. K8s-gatekeeperのインストール​

External webhook、Internal webhook、Helmの3つのインストール方法が利用可能です。

注

これらのインストール方法は評価目的専用です。本番環境へのデプロイメントの場合は、Chapter 5. Advanced settings を確認し、インストール前に必要なセキュリティ修正を適用してください。

2.1 Internal Webhook​

2.1.1 ステップ 1: イメージのビルド​

internal webhookデプロイメントの場合、K8s-gatekeeperはKubernetesサービスとして実行されます。イメージをビルドします:

docker build --target webhook -t k8s-gatekeeper .

これにより、'k8s-gatekeeper:latest' という名前のローカルイメージが作成されます。

注

minikubeユーザーは、'docker build' の前に eval $(minikube -p minikube docker-env) を実行してください。

2.1.2 ステップ 2: サービスとリソースのデプロイ​

これらのコマンドを実行します:

kubectl apply -f config/rbac.yaml
kubectl apply -f config/webhook_deployment.yaml 
kubectl apply -f config/webhook_internal.yaml

kubectl get pods を使用してデプロイを確認します。

2.1.3 ステップ 3: CRD リソースのインストール​

カスタムリソース定義をインストールします:

kubectl apply -f config/auth.casbin.org_casbinmodels.yaml 
kubectl apply -f config/auth.casbin.org_casbinpolicies.yaml

2.2 外部 Webhook​

外部 webhook デプロイの場合、K8s-gatekeeper は Kubernetes の外側で実行されます。Kubernetes では admission webhook に HTTPS が必要です。テスト用の証明書と秘密鍵（本番環境用ではありません）を提供しています。カスタム証明書については、第 5 章. 高度な設定 を参照してください。

提供されている証明書は 'webhook.domain.local' 向けに発行されています。hosts ファイル（例: /etc/hosts）を更新し、'webhook.domain.local' が K8s-gatekeeper が実行されている IP アドレスを指すようにしてください。

実行:

go mod tidy
go mod vendor
go run cmd/webhook/main.go
kubectl apply -f config/auth.casbin.org_casbinmodels.yaml 
kubectl apply -f config/auth.casbin.org_casbinpolicies.yaml
kubectl apply -f config/webhook_external.yaml

2.3 Helm によるインストール​

2.3.1 ステップ 1: イメージのビルド​

第 2.1.1 章 を参照してください。

2.3.2 Helm インストール​

実行: helm install k8sgatekeeper ./k8sgatekeeper

3. K8s-gatekeeper の使用​

3.1 Casbin モデルとポリシーの作成​

kubectl または提供されている Go クライアントを使用して、モデルとポリシーを作成します。

3.1.1 kubectl による作成/更新​

K8s-gatekeeper では、Casbin モデルは 'CasbinModel' CRD リソースとして保存されます。定義は config/auth.casbin.org_casbinmodels.yaml にあります。

example/allowed_repo/model.yaml の例を参照してください。重要なフィールド:

  • metadata.name: モデル名。K8s-gatekeeper によって正しくペアリングされるには、関連する CasbinPolicy オブジェクトの名前と一致する必要があります。
  • spec.enable: このモデルとその関連ポリシーを無効にする場合は "false" に設定します。
  • spec.modelText: Casbin モデル定義を含む文字列。

Casbin ポリシーは 'CasbinPolicy' CRD リソースとして保存され、config/auth.casbin.org_casbinpolicies.yaml に定義されています。

example/allowed_repo/policy.yaml の例を参照してください。重要なフィールド:

  • metadata.name: ポリシー名。関連する CasbinModel オブジェクトの名前と一致する必要があります。
  • spec.policyItem: Casbin ポリシー定義を含む文字列。

CasbinModel および CasbinPolicy ファイルを適用します:

kubectl apply -f <filename>

K8s-gatekeeper は、新しい CasbinModel/CasbinPolicy ペアを 5 秒以内に検出します。

3.1.2 Go クライアントによる作成/更新​

クラスターノードへの直接シェルアクセスが実用的でないシナリオ（例えば、自動化されたクラウドプラットフォームを構築する場合など）では、CasbinModel および CasbinPolicy リソースを管理するための Go クライアントを提供しています。

Go クライアントライブラリは pkg/client にあります。

client.go で、クライアントを作成するためにこの関数を使用します:

func NewK8sGateKeeperClient(externalClient bool) (*K8sGateKeeperClient, error)

externalClient パラメーターは、K8s-gatekeeper が Kubernetes クラスターの内側か外側で実行されているかを示します。

model.go では、CasbinModel の作成、削除、変更を行うための関数が提供されています。使用例については model_test.go を参照してください。

policy.go では、CasbinPolicy の作成、削除、変更を行うための関数が提供されています。使用例については policy_test.go を参照してください。

3.1.2 K8s-gatekeeper のテスト​

example/allowed_repo からモデルとポリシーを作成した後、次でテストします:

kubectl apply -f example/allowed_repo/testcase/reject_1.yaml

Kubernetes はこのリクエストを拒否し、理由として webhook を挙げるはずです。しかし、example/allowed_repo/testcase/approve_2.yaml を適用すると成功するはずです。

4. K8s-gatekeeper 向けのモデルとポリシーの作成​

続行する前に、Casbin の Model とポリシー構文を理解していることを確認してください。理解していない場合は、まず Get Started セクションをお読みください。この章では、Casbin のモデルとポリシーに精通していることを前提としています。

4.1 リクエスト定義​

K8s-gatekeeper がリクエストを評価する際、入力は常に AdmissionReview Go オブジェクトです。エンフォーサーは次のように使用されます:

ok, err := enforcer.Enforce(admission)

ここで admission は、Kubernetes の公式 Go API "k8s.io/api/admission/v1" にある AdmissionReview オブジェクトです。構造体定義は以下で入手できます: https://github.com/kubernetes/api/blob/master/admission/v1/types.go。追加のドキュメント: https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#webhook-request-and-response。

K8s-gatekeeper モデルでは、request_definition は常にこの形式に従う必要があります:

    [request_definition]
    r =  obj

[matchers] セクションで一貫して使用されている限り、名前 'obj' は変更できます。

4.2 モデルマッチャー​

ルールを記述するために Casbin の ABAC 機能を使用します。ただし、Casbin の式評価器はマップ/配列のインデックス参照や配列展開をネイティブにはサポートしていません。K8s-gatekeeper はこれを解決するための拡張関数を備えています。追加の機能が必要な場合は、issue を作成するか pull request を提出してください。

Casbin 関数の背景については、Function を参照してください。

拡張関数:

4.2.1 拡張関数​

4.2.1.1 access​

access 関数はマップおよび配列のインデックス参照を可能にします。example/allowed_repo/model.yaml を参照してください:

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") == p.obj

ここで、access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") は r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Image と同等です。r.obj.Request.Object.Object.Spec.Template.Spec.Containers はスライスです。

access は単一の値を返す引数なしの関数も呼び出すことができます。example/container_resource_limit/model.yaml を参照してください:

[matchers]
  m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
  parseFloat(access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","cpu","Value")) >= parseFloat(p.cpu) && \
  parseFloat(access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","memory","Value")) >= parseFloat(p.memory)

ここで、access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","cpu","Value") は r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Resources.Limits["cpu"].Value() と等しくなります。r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Resources.Limits はマップであり、Value() は単一の値を返す引数なしの関数です。

4.2.1.2 accessWithWildcard​

for ループを使用せずにすべての配列要素に対する条件（例えば、「すべての要素が 'aaa' で始まる必要がある」）を確認するには、マップ/スライス展開を用いて accessWithWildcard を使用します。

a.b.c が配列 [aaa,bbb,ccc,ddd,eee] である場合、accessWithWildcard(a,"b","c","*") はスライス [aaa,bbb,ccc,ddd,eee] を返します。ワイルドカード * はスライスを展開します。

複数のワイルドカードがサポートされています。例えば、accessWithWildcard(a,"b","c","*","*") は [a.b.c[0][0], a.b.c[0][1], ..., a.b.c[1][0], a.b.c[1][1], ...] を返します。

4.2.1.3 可変長引数関数​

Casbin の式評価器は、配列を可変長引数として自動的に展開します。これを利用して配列/スライス/マップを展開するため、いくつかの関数が配列/スライスを受け取ります:

  • contain(): 複数のパラメータを受け取り、最後のパラメータを除くいずれかのパラメータが最後のパラメータと等しいかどうかを返します。
  • split(a,b,c...,sep,index): [splits(a,sep)[index], splits(b,sep)[index], splits(c,sep)[index], ...] を返します。
  • len(): 可変長引数の数を返します。
  • matchRegex(a,b,c...,regex): すべてのパラメータ（a, b, c, ...）が正規表現に一致するかどうかを返します。

example/disallowed_tag/model.yaml からの例:

    [matchers]
    m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
    contain(split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj)

accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image") が ["a:b", "c:d", "e:f", "g:h"] を返す場合、split 操作は各要素を可変長引数サポート付きで処理し、それぞれからインデックス 1 を選択します。したがって、split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) は ["b","d","f","h"] を返します。最後に、contain(split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj) は p.obj が ["b","d","f","h"] に存在するかどうかを確認します。

4.2.1.2 型変換関数​

  • ParseFloat(): 整数を浮動小数点数に変換します（比較には浮動小数点型が必要なため必須）。
  • ToString(): オブジェクトを文字列に変換します。オブジェクトは基盤となる文字列型（例えば、type XXX string）を持つ必要があります。
  • IsNil(): パラメータが nil かどうかを返します。

5. 高度な設定​

5.1 証明書設定​

Kubernetes では Webhook が HTTPS を使用することが要求されます。2 つのオプションがあります:

  • 自己署名証明書（このリポジトリの例で使用）
  • 公開信頼済み証明書

5.1.1 自己署名証明書​

自己署名証明書は、公開的に認識されていない認証局（CA）を使用します。Kubernetes にこの CA を信頼させるよう設定する必要があります。

リポジトリの例では、秘密鍵と証明書を config/certificate/ca.key および config/certificate/ca.crt に保存したカスタム CA を使用しています。Webhook 証明書 config/certificate/server.crt は、この CA によってドメイン "webhook.domain.local"（外部 Webhook）および "casbin-webhook-svc.default.svc"（内部 Webhook）用に発行されています。

CA 情報は、Webhook 設定ファイルを介して Kubernetes に渡されます。config/webhook_external.yaml と config/webhook_internal.yaml の両方に、base64 でエンコードされた CA 証明書を格納する "CABundle" フィールドが含まれています。

証明書やドメインを変更する場合（例：Webhook を別の名前空間に移動したり、ドメインを変更したりする場合）：

  1. 新しい CA を生成します：

    • CA 秘密鍵を生成します：

      openssl genrsa -des3 -out ca.key 2048

    • パスワード保護を削除します：

      openssl rsa -in ca.key -out ca.key

  2. Webhook サーバーの秘密鍵を生成します：

    openssl genrsa -des3 -out server.key 2048
    openssl rsa -in server.key -out server.key

  3. CA を使用して Webhook 証明書に署名します：

    • システムの OpenSSL 設定ファイル（openssl version -a で確認でき、通常は openssl.cnf です）をコピーします。

    • 設定ファイルを修正します：

      • [req] セクションに req_extensions = v3_req を追加します。

      • [v3_req] セクションに subjectAltName = @alt_names を追加します。

      • 以下を追記します：

        [alt_names]
        DNS.2=<Your desired domain>

        注意：変更した場合は、'casbin-webhook-svc.default.svc' を実際のサービス名に置き換えてください。

    • 証明書リクエストを生成します：

      openssl req -new -nodes -keyout server.key -out server.csr -config openssl.cnf

    • CA を使用して証明書に署名します：

      openssl x509 -req -days 3650 -in server.csr -out server.crt -CA ca.crt -CAkey ca.key -CAcreateserial -extensions v3_req -extensions SAN -extfile openssl.cnf

  4. config/webhook_external.yaml と config/webhook_internal.yaml の 'CABundle' フィールドを、base64 でエンコードされた新しい CA 証明書で更新します。

  5. Helm デプロイメントの場合は、Helm チャートにも同様の適用を行います。

5.1.2 Publicly Trusted Certificates​

公開信頼済み証明書を使用する場合は、上記の手順をスキップしてください。config/webhook_external.yaml と config/webhook_internal.yaml から "CABundle" フィールドを削除し、ドメインに登録済みのドメインを設定します。
