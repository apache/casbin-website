RBAC vs ABAC vs ACL vs ReBAC: アクセス制御モデルの選択

アクセス制御モデルの違いは、たった一つのことです：認可判断の根拠です。

RBAC vs ABAC（簡潔に）： RBACは権限をロールに付与し、ユーザーにロールを割り当てるため、「編集者は何ができるか？」には簡単に答えられますが、ドキュメントごとに「自分のものだけ」というルールを作るのは困難です（ドキュメント毎にロールが必要になるため）。一方、ABACはユーザー、リソース、環境の属性に対する条件を評価するため、所有権、部門、時間などのルールを自然に扱えますが、監査は難しくなります。多くのアプリケーションでは、機能単位でRBACを使い、レコード単位でABACの条件を追加します。このページの最後の例では、1つのCasbin Model で両方を実現しています。

モデル判断基準ルールの例
ACL (Access Control List)ユーザーalice は design.md を編集できる
RBAC (Role-Based Access Control)ユーザーのロールeditors はドキュメントを編集できる
ABAC (Attribute-Based Access Control)ユーザー、リソース、コンテキストの属性オーナーは自分のドキュメントを編集できる。同じ部門の人は閲覧できる
ReBAC (Relationship-Based Access Control)ユーザーとリソース間の関係性フォルダの viewer である人は、その中のドキュメントを閲覧できる
PBAC (Policy-Based Access Control)ポリシーとして保存されたルール式ポリシー行に含まれる任意の条件

これらは競合する製品ではなく、ルールを記述する方法であり、実際のシステムでは混在して使われます。Casbinでは、それぞれが数行の Model 設定で表現でき、アプリケーションコードを変更せずに切り替えたり組み合わせたりできます。このページでは、小さな例を各モデルで表現し、違いを具体的に示します。

例： ドキュメントアプリを考えます。ドキュメントは1つ (design.md) で、オーナーは alice です。alice は編集でき、bob は閲覧できますが、それ以外のユーザーはアクセスできません。

ACL​

Access Control List は、各ユーザーに対して、各オブジェクトで何ができるかを明示的に記述します。

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act
p, alice, design.md, read
p, alice, design.md, edit
p, bob, design.md, read
  • 得意な点： 小規模なシステムや、オブジェクト単位の共有（"このファイルを bob と共有する"）。すべての判断が容易に説明可能です。
  • 苦手な点： スケール。u 人のユーザーと o 個のオブジェクトがある場合、リストは u × o 行に膨らみます。また、誰かの所属が変わった際、その人のすべての行を探して修正する必要があります。

RBAC​

Role-Based Access Control は、ユーザーと権限の間にロールを置きます。権限はロールに付与され、ユーザーにはロールが割り当てられます。

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
p, editor, design.md, read
p, editor, design.md, edit
p, viewer, design.md, read

g, alice, editor
g, bob, viewer
g, carol, viewer

carol に読み取り権限を与えるのは、g 行1つで済みます。彼女は viewer が持つすべての権限を継承します。ロールは他のロールから継承することも可能で（g, editor, viewer）、RBAC with domains を使えば、異なるテナントで異なるロールをユーザーに付与できます。

  • 得意な点： 職務機能に基づく権限管理。監査が容易で（"editor は何ができるか？"、"admin は誰か？"）、入退社時の処理もロール変更だけで済みます。
  • 苦手な点： 特定のレコードに関するルール。「著者は自分の記事のみ編集できる」といったルールは、ロールだけでは表現できません。無理に実現しようとすると、レコードごとにロールを作成することになり、これは「ロール爆発 (role explosion)」と呼ばれます。

RBAC vs ACL: ACL はロールのない RBAC です。ユーザー数がごく少数でない限り、RBAC から始めることを推奨します。後からロールを追加するのは、すべてのルールを書き直すことにつながるからです。

チュートリアル: Go, Node.js, NestJS, Python, Java, Rust, gRPC.

ABAC​

Attribute-Based Access Control は、ユーザーの属性（部門、セキュリティクリアランス）、リソースの属性（オーナー、ステータス、機密レベル）、環境の属性（時間、IPアドレス）に対する条件を評価します。Casbin では、オブジェクトを Enforce() に渡し、matcher でそのフィールドを読み取ります。

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = r.sub.Name == r.obj.Owner || (r.act == 'read' && r.sub.Department == r.obj.Department)

ポリシーファイルはありません。alice が design.md を編集できるのは彼女がオーナーだからであり、bob が閲覧できるのは彼が同じ部門にいるからです。design 部門にある新しいドキュメントも、ルールの変更なしに bob が閲覧できます。

  • 得意な点： レコードやコンテキストに依存するルール：所有権、部門、ドキュメントステータス、営業時間、地域など。1つのルールで多数のロール付与を置き換えられます。
  • 苦手な点： 監査。「このドキュメントを閲覧できるのは誰か？」に対する直接的な答えがなく、すべてのユーザーに対して条件を評価する必要があります。また、チェック前にレコードを読み込んで属性を取得しておく必要があります。

eval() パターン を使用すると、条件を Model からポリシー行へ移動できるため、他のルールと同様に実行時に追加・削除が可能になります。

チュートリアル: Go, Node.js with Express, Python with Flask.

ReBAC​

Relationship-Based Access Control は、関係性から権限を導き出します。alice は design.md の owner であり、bob は viewer です。owner は編集でき、viewer は閲覧できます。これは Google Zanzibar とそのオープンソース派生システムの背後にあるモデルです。

[request_definition]
r = sub, obj, act

[policy_definition]
p = relation, obj_type, act

[role_definition]
g = _, _, _
g2 = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, r.obj, p.relation) && g2(r.obj, p.obj_type) && r.act == p.act
p, owner, doc, read
p, owner, doc, edit
p, viewer, doc, read

g, alice, design.md, owner
g, bob, design.md, viewer
g, bob, roadmap.md, owner

g2, design.md, doc
g2, roadmap.md, doc

bob は自分がオーナーである roadmap.md を編集できますが、design.md は閲覧のみ可能です。p ルールは、オブジェクトタイプ全体に対してある関係性が何を許可するかを一度定義し、g 行は誰がどのオブジェクトに対してどの関係性を持つかを記録します。

  • 得意な点： 共有とコラボレーション（ドキュメント、フォルダ、プロジェクト、組織）。特に、organization → folder → document のような階層構造を通じて権限が継承される場合に有効です。
  • 苦手な点： 小規模またはフラットなシステムでは、過剰な仕組みとなります。オブジェクト作成時や共有時に常に関係性を記述する必要があります。

完全な Model については ReBAC を参照してください。専用の Zanzibar スタイルのサービスを検討している場合は、Casbin vs. OpenFGA もご覧ください。

PBAC​

Policy-Based Access Control は独立したモデルというよりは、他のモデルを記述するための方法論です。ルール自体がポリシーとして保存された式であり、実行時に評価されます。Casbin では、ABAC チュートリアルや PBAC ページで使用されている eval() パターンがこれに該当します。その価値は運用面にあります。セキュリティやコンプライアンスチームが、コードリリースなしにルールを変更できるようになります。

選択方法​

  1. まず RBAC から始めましょう。 権限を職務機能 ("admins", "editors", "billing") で説明できる場合、RBAC は拡張性があり監査が最も容易なシンプルなモデルです。
  2. 所有権とコンテキストのために ABAC 条件を追加します。 「自分のものだけ」や「営業時間中だけ」といった要件が生じた場合は、ロールを増やすのではなく条件を追加してください。
  3. 共有が製品の中核である場合は ReBAC を選択します。 ユーザー同士がオブジェクトを共有し、フォルダ、プロジェクト、組織を通じてアクセスが継承される場合、関係を直接モデル化してください。
  4. マルチテナンシーには domains を使用します。 同じユーザーが異なる組織で異なる役割を持つ場合、他の選択肢に関わらず RBAC with domains を使用してください。
  5. 必須のモデルは必要な場合のみ検討します。 BLP, Biba, and LBAC は、政府や防衛などの分類レベルがある環境に適しています。

RBAC と ABAC の組み合わせ​

ほとんどのアプリケーションはこの形になります。ロールによってユーザーが到達できる機能を決定し、属性によって触れられるレコードに絞り込みます。このモデルでは、管理者は任意のドキュメントを編集できますが、著者は自分が所有するドキュメントのみを編集できます:

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub.Name, p.sub) && r.obj.Type == p.obj && r.act == p.act && (p.sub == 'admin' || r.sub.Name == r.obj.Owner)
p, admin, doc, edit
p, author, doc, edit

g, erin, admin
g, alice, author
g, bob, author

design.md (type doc, owner alice) の場合、alice は著者かつ所有者なので編集でき、erin は管理者なので編集できますが、bob は著者ですが所有者ではないため編集できません。

FAQ​

RBACとABACの違いは何ですか？ RBACはロールに権限を付与し、ユーザーにロールを割り当てるため、「編集者は何ができるか？」という質問に答えます。ABACはユーザー、リソース、環境の属性に対する条件を評価するため、「このユーザーは今、このレコードを編集してもよいか？」という質問に答えます。RBACは監査が容易であり、ABACはレコードごとにロールを設定することなく、所有権、部門、時間のルールを表現できます。ほとんどのアプリケーションでは、上記の複合例のように、機能に対してはロールを使用し、レコードに対しては属性条件を使用します。

ABAC は RBAC より安全ですか? どちらかが本質的に安全というわけではありません。ABAC はより細かなルールを表現できますが、その決定事項の監査は困難です。RBAC は粗いですがレビューが容易です。安全性は、意図したものと一致するルール、およびそれが一致していることを確認できることに由来します。

最初に RBAC を始めて後で ABAC に移行できますか? はい。Casbin では、モデルは設定ファイルであり、アプリケーションは同じ Enforce() メソッドを呼び出すため、matcher に条件を追加したり、上記のように両者を組み合わせたりしても、認可呼び出しを書き直す必要はありません。

PBAC はどこに位置付けられますか? PBAC は、ルールがどのように管理されるか (実行時に評価されるポリシーデータとして) を説明するものであり、ルールが何を基準にするかを説明するものではありません。Casbin のポリシーはすべてのモデルでデータであるため、上記のどのモデルもこの方法で管理できます。

RBAC と ABAC の両方をサポートするライブラリやプラットフォームはどこですか? Casbin は Go、Java、Node.js、Python、.NET、Rust およびその他の言語で、1 つのモデル内で両方とその組み合わせをサポートしています。OPA や Cedar などのポリシーエンジンも両方を表現できますが、OpenFGA などの Zanzibar スタイルのサービスは ReBAC を中心に構築されています。Casbin vs. Alternatives でそれらを比較しています。

Casbin はこれらすべてをサポートしていますか? はい、RBAC96、OrBAC、UCON、LBAC、Biba 完全性モデル、優先度と deny-override ポリシーなども含めてサポートしています。Supported models を参照し、online editor で試してみてください。Super administrators は、別のモデルではなく、追加の matcher 条件 1 つで処理されます。
