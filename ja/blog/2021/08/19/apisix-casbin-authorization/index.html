APISIXでのCasbinを用いた認可

2021年8月19日 · 1分読む
Rushikesh Tote
Member of Casbin
Yilia Lin
Apache APISIX Committer

はじめに​

Apache APISIX は、組み込みの authz-casbin プラグインを使用してゲートウェイでCasbin認可ポリシーを適用できます。このプラグインは Lua Casbin を使用し、ACL、RBAC、ABACなどのアクセス制御モデルをサポートします。

このガイドでは、APISIXのリクエストパス上に小さなRBACポリシーを設定します。許可および拒否されたリクエストを検証した後、ルートを変更せずにプラグインメタデータを介して共有ポリシーを更新します。

Casbinコミュニティは当初、APISIX Issue #4674 でこの統合を提案し、APISIX PR #4710 でプラグインを追加しました。

2026年8月 リフレッシュ

このガイドは2026年8月にリフレッシュされました。例は Apache APISIX 3.17.0 で検証済みです。元の2021年の著者は引き続きクレジットされ、2026年のリフレッシュに対してYilia Linが追加されました。

認証境界

Casbinは認可を実行しますが、認証は実行しません。この例ではテストを小さく保つために、user リクエストヘッダーのみを主体として使用しています。本番環境では、クライアントから直接提供されるIDヘッダーを信頼しないでください。認証レイヤーまたは信頼できるプロキシがIDを確立し、Casbinがリクエストを評価する前に信頼できない値を削除または上書きする必要があります。

前提条件と開始状態​

このガイドは、すでに稼働中の使い捨て可能な Apache APISIX 3.17.0 インスタンスから始まります。ローカルインスタンスが必要な場合は、APISIX Dockerデプロイメントガイド に従い、APISIXイメージを apache/apisix:3.17.0-debian に固定してください。

インスタンスには以下が必要です：

  • データプレーンが http://127.0.0.1:9080 で利用可能であること；
  • http://127.0.0.1:9180 で利用可能な Admin API;
  • 組み込みの authz-casbin プラグインと mocking プラグインが有効化されていること。

curl と jq も必要です。Admin API に設定されたキーを admin_key に指定してください:

export admin_key='<your-admin-api-key>'

プレースホルダーを置き換えてから続行します。Admin API が到達可能であり、プラグインが有効になっていることを確認してください:

curl --fail-with-body \
  "http://127.0.0.1:9180/apisix/admin/plugins/list" \
  -H "X-API-KEY: $admin_key" | \
jq -e '(["authz-casbin", "mocking"] - .) | length == 0'

コマンドは true を出力するはずです。Admin API を信頼できないネットワークに公開したり、デモ用の認証情報を他の環境で再利用したりしないでください。

Model と Policy の定義​

プラグインは以下の 3 つのリクエスト値を評価します:

  • sub: 設定されたリクエストヘッダーからのサブジェクト;
  • obj: リクエスト URI パス; および
  • act: HTTP メソッド。

model.conf を作成します:

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = (g(r.sub, p.sub) || keyMatch(r.sub, p.sub)) && keyMatch(r.obj, p.obj) && keyMatch(r.act, p.act)

policy.csv を作成します:

p, *, /anything, GET
p, admin, *, *
g, alice, admin

このポリシーにより、任意のサブジェクトが GET /anything を送信できるようになります。また、alice に admin ロールを割り当てており、このロールはすべてのパスに対するすべてのメソッドへのアクセス権限を持ちます。

共有ポリシーをプラグインメタデータに保存する​

ファイルを JSON 文字列として読み込み、APISIX プラグインメタデータに書き込みます:

jq -n \
  --rawfile model model.conf \
  --rawfile policy policy.csv \
  '{model: $model, policy: $policy}' | \
curl --fail-with-body \
  "http://127.0.0.1:9180/apisix/admin/plugin_metadata/authz-casbin" \
  -H "X-API-KEY: $admin_key" \
  -H "Content-Type: application/json" \
  -X PUT \
  --data-binary @-

プラグインメタデータを使用すると、独自にルートローカルな Model と Policy を定義せずに authz-casbin を有効化するルートに対して、単一の Model と Policy を提供できます。

ルートでの認可の有効化​

ルートを作成し、プラグインに対して user ヘッダーからサブジェクトを読み取るよう指示します:

curl --fail-with-body \
  "http://127.0.0.1:9180/apisix/admin/routes/casbin-demo" \
  -H "X-API-KEY: $admin_key" \
  -H "Content-Type: application/json" \
  -X PUT \
  -d '{
    "uri": "/*",
    "plugins": {
      "authz-casbin": {
        "username": "user"
      },
      "mocking": {
        "_meta": {
          "priority": 1000
        },
        "response_status": 200,
        "response_example": "{\"message\":\"authorized\"}"
      }
    },
    "upstream": {
      "type": "roundrobin",
      "nodes": {
        "127.0.0.1:1": 1
      }
    }
  }'

このルートはローカルに username フィールドのみを定義しているため、プラグインメタデータにある Model と Policy を使用します。ルートローカルな Model と Policy が設定されている場合、それらはプラグインメタデータよりも優先されます。

mocking プラグインにより、許可されたリクエストは決定論的なローカルレスポンスを受け取るため、この例ではパブリックアップストリームに依存しません。そのルートローカルな優先度は authz-casbin よりも低く、これにより認可判定が最初に実行されます。したがって、到達不能なアップストリームには接続されません。この優先度オーバーライドとモックレスポンスはテスト用のフィクスチャであり、本番環境での推奨事項ではありません。

許可および拒否判定の確認​

公開パスへの匿名リクエストは許可されます:

curl -i http://127.0.0.1:9080/anything

期待されるステータス:

HTTP/1.1 200 OK
{"message":"authorized"}

bob は admin ロールを持たないため、別のパスは拒否されます:

curl -i http://127.0.0.1:9080/anything/res -H 'user: bob'

期待される結果:

HTTP/1.1 403 Forbidden
{"message":"Access Denied"}

alice は admin ロールを持つため、同じリクエストは許可されます:

curl -i http://127.0.0.1:9080/anything/res -H 'user: alice'

期待されるステータス:

HTTP/1.1 200 OK
{"message":"authorized"}

共有ポリシーの更新​

policy.csv に bob 向けの直接権限を追加します:

p, *, /anything, GET
p, admin, *, *
p, bob, /anything/res, GET
g, alice, admin

プラグインメタデータのコマンドを再度実行します。このメタデータを参照するルートは、ルート設定を変更することなく更新後のポリシーを使用します。リクエストを繰り返します:

curl -i http://127.0.0.1:9080/anything/res -H 'user: bob'

期待される結果は次のようになります:

HTTP/1.1 200 OK
{"message":"authorized"}

設定スコープの選択​

複数のルートで単一の Model と Policy を共有する必要がある場合は、プラグインメタデータを使用します。ルートごとに独立した認可構造が必要な場合は、ルートローカルな Model と Policy を使用します。完全な設定スキーマおよびファイルベースの代替手段については、APISIX authz-casbin プラグインリファレンスを参照してください。

クリーンアップ​

テスト用ルートを削除します:

curl --fail-with-body \
  "http://127.0.0.1:9180/apisix/admin/routes/casbin-demo" \
  -H "X-API-KEY: $admin_key" \
  -X DELETE

共有プラグインメタデータを削除します:

curl --fail-with-body \
  "http://127.0.0.1:9180/apisix/admin/plugin_metadata/authz-casbin" \
  -H "X-API-KEY: $admin_key" \
  -X DELETE
