Aggiornamento di Casbin (Go) da v2 a v3: Una guida completa alla migrazione

1 febbraio 2026 · Lettura di 9 minuti
Yang Luo
Creator of Casbin

Se state eseguendo Casbin v2 in produzione e vi chiedete quale sia la procedura di aggiornamento a v3, questa guida fa per voi. Copriremo tutto ciò che c'è da sapere sulla transizione, dalla comprensione delle modifiche all'esecuzione di una migrazione sicura in produzione.

Cosa è cambiato nella v3?​

La buona notizia: la v3 è principalmente una modifica del percorso del modulo con piena compatibilità all'indietro. La logica principale di autorizzazione, le API e le funzionalità rimangono invariate. Questa è stata una decisione intenzionale per minimizzare le interruzioni seguendo le convenzioni di versioning semantico di Go.

La modifica principale: Percorso del modulo​

L'unica modifica incompatibile nella v3 è il percorso del modulo Go:

// v2
import "github.com/casbin/casbin/v2"

// v3
import "github.com/casbin/casbin/v3"

Questo è tutto. Le vostre policy, modelli e logica di codice esistenti non devono essere modificati. La migrazione è meccanica: aggiornate le istruzioni di import e il vostro file go.mod.

Perché rilasciare la v3?​

Potreste chiedervi perché rilasciare una nuova versione major solo per una modifica al percorso di import. La risposta è il versioning semantico. Il sistema dei moduli di Go utilizza il numero della versione major nel percorso di import (/v2, /v3, ecc.). Ciò consente a più versioni major di coesistere nello stesso albero delle dipendenze, fondamentale per grandi applicazioni con molte dipendenze.

Rilasciando la v3, abbiamo:

  • Allineato con il versioning semantico degli import di Go
  • Abilitato la migrazione graduale in grafi di dipendenza complessi
  • Preparato il terreno per futuri miglioramenti senza rompere gli utenti v2 esistenti

Cosa è rimasto uguale?​

Tutto il resto. Davvero.

  • Tutte le API rimangono identiche - Enforce(), AddPolicy(), GetAllRoles() e ogni altro metodo funziona esattamente come prima
  • Sintassi di modello e policy invariata - I vostri file di modello .conf e i file di policy .csv esistenti funzionano senza modifiche
  • Interfaccia Adapter invariata - I metodi persist.Adapter sono gli stessi; agli adapter serve solo una release compilata contro il percorso del modulo v3
  • Caratteristiche prestazionali - Nessuna regressione o miglioramento delle prestazioni; è lo stesso motore
  • Integrazioni middleware - Il middleware funziona allo stesso modo una volta che importa la stessa versione major del vostro enforcer

Nuove funzionalità nella v3​

Dalla release v3.0.0 di dicembre 2025, diverse nuove funzionalità sono state aggiunte:

v3.7.0+: Integrazione avanzata del Logger​

Ora è possibile integrare logger personalizzati nelle operazioni principali di enforcement e gestione delle policy di Casbin, fornendo migliore osservabilità:

enforcer.SetLogger(yourCustomLogger)

v3.8.0+: API GetAllUsers()​

Una nuova API per distinguere gli utenti dai ruoli:

users, err := enforcer.GetAllUsers()

È particolarmente utile nei sistemi RBAC dove è necessario elencare gli utenti effettivi separatamente dalle definizioni dei ruoli.

v3.9.0+: Rilevamento cicli integrato​

L'enforcer include ora il rilevamento automatico dei cicli nelle gerarchie dei ruoli, prevenendo loop infiniti:

// Automatically detects and prevents circular role assignments
enforcer.AddGroupingPolicy("alice", "admin")
enforcer.AddGroupingPolicy("admin", "alice") // Will be detected as a cycle

v3.10.0+: API Explain() per approfondimenti sull'autorizzazione basati su AI​

La funzionalità più recente sfrutta le API LLM per spiegare le decisioni di autorizzazione in linguaggio naturale:

enforcer.SetAIConfig(casbin.AIConfig{
    Endpoint: "https://api.openai.com/v1/chat/completions",
    APIKey:   os.Getenv("OPENAI_API_KEY"),
    Model:    "gpt-4",
})

explanation, err := enforcer.Explain("alice", "data1", "read")
// e.g. "Alice can read data1 because she has the 'reader' role..."

Ciò è particolarmente prezioso per il debug di policy complesse e per aiutare gli stakeholder non tecnici a comprendere le decisioni di autorizzazione.

Strategia di Migrazione​

Per Nuovi Progetti​

Semplice: usa v3 fin dall'inizio.

go get github.com/casbin/casbin/v3
import "github.com/casbin/casbin/v3"

Per Progetti Esistenti in v2​

La migrazione prevede tre passaggi:

Passaggio 1: Aggiorna il tuo go.mod​

go get github.com/casbin/casbin/v3
go mod tidy

Passaggio 2: Aggiorna le Dichiarazioni di Import​

Trova e sostituisci tutti gli import Casbin nel tuo codebase:

# Using sed on Unix/Linux/Mac
find . -type f -name '*.go' -exec sed -i 's|github.com/casbin/casbin/v2|github.com/casbin/casbin/v3|g' {} +

# Or manually in your editor
# Find: github.com/casbin/casbin/v2
# Replace: github.com/casbin/casbin/v3

Passaggio 3: Aggiorna gli Import degli Adapter (Se Applicabile)​

Un adapter implementa persist.Adapter da una specifica versione principale, poiché model.Model in casbin/v2 e casbin/v3 sono tipi Go diversi. Un enforcer v3 necessita quindi di una release dell'adapter che importa github.com/casbin/casbin/v3. Controlla il go.mod dell'adapter:

// Example: the PostgreSQL adapter already depends on casbin/v3
import pgadapter "github.com/apache/casbin-pg-adapter"

// The file adapter is built in and ships with each major version

Se il tuo adapter non è ancora stato aggiornato, rimani su v2 per quel servizio fino a quando non lo sarà, oppure apri un issue nel repository dell'adapter.

Piano di Rollback​

Se devi effettuare un rollback:

  1. Livello Codice: Annulla le modifiche agli import (utilizza il controllo di versione)
  2. Livello Dipendenza: go get github.com/casbin/casbin/v2@latest
  3. Deploy: Usa il tuo processo standard di deployment per annullare le modifiche

La bellezza di questa migrazione è che il rollback è banale - basta annullare le modifiche agli import e ridistribuire.

Devo Migrare il mio Database delle Policy?​

No. I tuoi dati esistenti delle policy rimangono invariati. Le policy sono memorizzate come semplici stringhe (subject, object, action, ecc.) e non hanno dipendenze dalla versione di Casbin.

Test della Migrazione​

Test Automatizzati​

I tuoi test esistenti dovrebbero passare senza modifiche:

func TestPolicyEnforcement(t *testing.T) {
    // This test works identically in v2 and v3
    e, _ := casbin.NewEnforcer("model.conf", "policy.csv")
    
    ok, _ := e.Enforce("alice", "data1", "read")
    if !ok {
        t.Error("Expected alice to have read access to data1")
    }
}

Test di Integrazione​

Il middleware che accetta un *casbin.Enforcer è legato a una specifica versione principale allo stesso modo degli adapter. Se il tuo middleware importa ancora casbin/v2, chiamare l'enforcer direttamente richiede poche righe:

// Example with Gin
import (
    "net/http"

    "github.com/casbin/casbin/v3"
    "github.com/gin-gonic/gin"
)

func Authorizer(e *casbin.Enforcer) gin.HandlerFunc {
    return func(c *gin.Context) {
        ok, err := e.Enforce(c.GetString("user"), c.Request.URL.Path, c.Request.Method)
        if err != nil || !ok {
            c.AbortWithStatus(http.StatusForbidden)
            return
        }
        c.Next()
    }
}

Test di Carico​

Esegui i tuoi standard load test sulla build v3. Le caratteristiche di performance dovrebbero essere identiche a v2.

Verifica delle Policy​

Confronta la valutazione delle policy tra le versioni:

# Export policies from v2
# Load into v3
# Run test cases against both
# Compare results

Se noti differenze, si tratta probabilmente di un bug - segnalalo!

Errori Comuni​

Errore Comune 1: Dipendenze Miste v2/v3​

Problema: Alcune dipendenze usano Casbin v2, altre usano v3, causando conflitti.

Soluzione: La build stessa funziona correttamente: il sistema di moduli di Go tratta v2 e v3 come pacchetti separati, quindi entrambi possono coesistere nello stesso albero delle dipendenze. Ciò che non puoi fare è passare un enforcer v3 a una libreria che ne aspetta uno v2. Mantieni l'enforcer, il suo adapter e il suo middleware sulla stessa versione principale.

Errore Comune 2: Disallineamento della Versione dell'Adapter​

Problema: Utilizzo di un adapter v2 con Casbin v3 (o viceversa).

Soluzione: Questo si manifesta come un errore di compilazione, non come una sorpresa runtime. Verifica quale versione principale di Casbin richiede il go.mod dell'adapter e usa una release che corrisponda al tuo enforcer.

Errore Comune 3: Dimenticare i Pacchetti Interni​

Problema: Aggiornati gli import dell'applicazione principale ma dimenticati quelli dei pacchetti interni o degli strumenti.

Soluzione: Usa go mod graph e go mod why per trovare tutte le dipendenze Casbin:

go mod graph | grep casbin

Errore Comune 4: Problemi di Compilazione degli Adapter Personalizzati​

Problema: L'adapter personalizzato non si compila dopo l'aggiornamento.

Soluzione: L'interfaccia dell'adapter non è cambiata, quindi questo suggerisce un problema di importazione. Verifica che tutti gli import di Casbin nel tuo adapter utilizzino v3:

import (
    "github.com/casbin/casbin/v3"
    "github.com/casbin/casbin/v3/persist"
)

FAQ​

D: La v2 è ancora mantenuta?​

Al momento della stesura di questa documentazione, la v2 riceve correzioni per bug critici, ma le nuove funzionalità sono sviluppate per la v3. Pianifica la migrazione entro i prossimi 6-12 mesi.

D: Posso migrare gradualmente avendo alcuni servizi sulla v2 e altri sulla v3?​

Sì! Possono persino condividere lo stesso database delle policy. Questo è uno dei vantaggi delle modifiche minime nella v3.

D: Il mio middleware (Gin, Echo, Fiber, ecc.) funzionerà?​

Solo se importa la stessa versione principale del tuo enforcer. Controlla il file go.mod del middleware; se è ancora sulla v2, chiama Enforce() da un piccolo handler tuo come mostrato sopra.

D: Devo aggiornare i miei file modello .conf?​

No. La sintassi dei file modello è invariata.

D: Devo aggiornare i miei file di policy .csv?​

No. Il formato dei file di policy è invariato.

D: Che dire di WatcherEx, FilteredAdapter e altre interfacce?​

Tutte le interfacce rimangono invariate. Se il tuo codice implementa queste interfacce, non sono necessarie modifiche (oltre ai percorsi di import).

D: Impatto sulle prestazioni?​

Nessuno. La v3 utilizza lo stesso motore di valutazione della v2.

D: Posso usare la v3 con Go 1.16?​

Controlla il file go.mod nel repository Casbin v3 per la versione minima supportata di Go. In generale, si consiglia di utilizzare l'ultima versione stabile di Go.

Buon aggiornamento!
