อัปเกรด Casbin (Go) จาก v2 เป็น v3: คู่มือการย้ายระบบฉบับสมบูรณ์

1 กุมภาพันธ์ 2569 · อ่าน 1 นาที
Yang Luo
Creator of Casbin

หากคุณกำลังใช้งาน Casbin v2 ใน production และสงสัยเกี่ยวกับขั้นตอนการอัปเกรดเป็น v3 คู่มือนี้เขียนมาเพื่อคุณ เราจะครอบคลุมทุกสิ่งที่ต้องรู้เกี่ยวกับการเปลี่ยนผ่าน ตั้งแต่การทำความเข้าใจว่าอะไรเปลี่ยนแปลงไป จนถึงวิธีการย้ายระบบอย่างปลอดภัยใน production

What Changed in v3?​

ข่าวดีคือ: v3 เป็นการเปลี่ยน module path เป็นหลักโดยมีความเข้ากันได้ย้อนหลังอย่างสมบูรณ์ ตรรกะการกำหนดสิทธิ์แกนกลาง, APIs และฟังก์ชันการทำงานยังคงเดิม นี่เป็นการตัดสินใจที่จงใจเพื่อลดผลกระทบให้น้อยที่สุดขณะปฏิบัติตามมาตรฐาน semantic versioning ของ Go

The Main Change: Module Path​

การเปลี่ยนแปลงที่ส่งผลกระทบต่อการใช้งาน (breaking change) เพียงอย่างเดียวใน v3 คือ Go module path:

// v2
import "github.com/casbin/casbin/v2"

// v3
import "github.com/casbin/casbin/v3"

แค่นั้นเอง Policies, models และตรรกะโค้ดที่มีอยู่ของคุณไม่จำเป็นต้องเปลี่ยนแปลง การย้ายระบบเป็นเพียงเชิงกลไก: อัปเดต import statements และไฟล์ go.mod ของคุณ

Why Release v3?​

คุณอาจสงสัยว่าทำไมถึงออกเวอร์ชัน major ใหม่เพียงเพื่อการเปลี่ยน import path คำตอบคือ semantic versioning ระบบ module ของ Go ใช้เลข major version ใน import path (/v2, /v3 ฯลฯ) ซึ่งทำให้สามารถมี major versions หลายเวอร์ชันอยู่ใน dependency tree เดียวกันได้ ซึ่งเป็นสิ่งสำคัญสำหรับแอปพลิเคชันขนาดใหญ่ที่มี dependencies จำนวนมาก

ด้วยการออก v3 เราได้:

  • สอดคล้องกับมาตรฐาน semantic import versioning ของ Go
  • เปิดโอกาสให้ย้ายระบบทีละขั้นใน dependency graphs ที่ซับซ้อน
  • วางรากฐานสำหรับการพัฒนาในอนาคตโดยไม่กระทบต่อผู้ใช้ v3 เดิม

What Stayed the Same?​

ทุกอย่างที่เหลือ จริงๆ นะ

  • All APIs remain identical - Enforce(), AddPolicy(), GetAllRoles() และวิธีอื่นๆ ทำงานเหมือนเดิมทุกประการ
  • Model and policy syntax unchanged - ไฟล์ model .conf และไฟล์ policy .csv ที่มีอยู่ของคุณทำงานได้โดยไม่ต้องแก้ไข
  • Adapter interface unchanged - วิธีต่างๆ ใน persist.Adapter ยังคงเดิม; adapters เพียงต้องการ release ที่ build ด้วย v3 module path
  • Performance characteristics - ไม่มีการถอยหลังหรือปรับปรุงด้านประสิทธิภาพ; เป็น engine ตัวเดิม
  • Middleware integrations - Middleware ทำงานเหมือนเดิมเมื่อ import major version เดียวกันกับ enforcer ของคุณ

New Features in v3​

นับตั้งแต่การปล่อยเวอร์ชัน v3.0.0 ในเดือนธันวาคม 2025 มีการเพิ่มฟีเจอร์ใหม่หลายอย่าง:

v3.7.0+: Enhanced Logger Integration​

คุณสามารถ integrate custom loggers เข้ากับการบังคับใช้ core enforcement และการจัดการ policy operations ของ Casbin เพื่อให้มี observability ที่ดีขึ้น:

enforcer.SetLogger(yourCustomLogger)

v3.8.0+: GetAllUsers() API​

API ใหม่สำหรับแยกแยะระหว่าง users กับ roles:

users, err := enforcer.GetAllUsers()

มีประโยชน์อย่างยิ่งในระบบ RBAC ที่คุณต้องแสดงรายการ actual users แยกจาก role definitions

v3.9.0+: Built-in Cycle Detection​

Enforcer ปัจจุบันรวมการตรวจจับ cycles ใน role hierarchies โดยอัตโนมัติ เพื่อป้องกัน infinite loops:

// Automatically detects and prevents circular role assignments
enforcer.AddGroupingPolicy("alice", "admin")
enforcer.AddGroupingPolicy("admin", "alice") // Will be detected as a cycle

v3.10.0+: Explain() API for AI-Powered Authorization Insights​

ฟีเจอร์ล่าสุดใช้ LLM APIs เพื่ออธิบายการตัดสินใจด้านการกำหนดสิทธิ์ด้วยภาษาธรรมชาติ:

enforcer.SetAIConfig(casbin.AIConfig{
    Endpoint: "https://api.openai.com/v1/chat/completions",
    APIKey:   os.Getenv("OPENAI_API_KEY"),
    Model:    "gpt-4",
})

explanation, err := enforcer.Explain("alice", "data1", "read")
// e.g. "Alice can read data1 because she has the 'reader' role..."

มีคุณค่าอย่างมากสำหรับการ debug policies ที่ซับซ้อน และช่วยให้ผู้มีส่วนได้ส่วนเสียที่ไม่ใช่สายเทคนิคเข้าใจการตัดสินใจด้านการกำหนดสิทธิ์

กลยุทธ์การย้ายระบบ​

สำหรับโปรเจกต์ใหม่​

ง่าย: เริ่มใช้งาน v3 ตั้งแต่แรกเลย

go get github.com/casbin/casbin/v3
import "github.com/casbin/casbin/v3"

สำหรับโปรเจกต์ v2 ที่มีอยู่เดิม​

การย้ายระบบประกอบด้วยสามขั้นตอน:

ขั้นตอนที่ 1: อัปเดต go.mod ของคุณ​

go get github.com/casbin/casbin/v3
go mod tidy

ขั้นตอนที่ 2: อัปเดต Import Statements​

ค้นหาและแทนที่ import ของ Casbin ทั้งหมดใน codebase ของคุณ:

# Using sed on Unix/Linux/Mac
find . -type f -name '*.go' -exec sed -i 's|github.com/casbin/casbin/v2|github.com/casbin/casbin/v3|g' {} +

# Or manually in your editor
# Find: github.com/casbin/casbin/v2
# Replace: github.com/casbin/casbin/v3

ขั้นตอนที่ 3: อัปเดต Adapter Imports (ถ้ามี)​

Adapter ต้อง implement persist.Adapter จากเวอร์ชันหลักใดเวอร์ชันหนึ่งโดยเฉพาะ เนื่องจาก model.Model ใน casbin/v2 และ casbin/v3 เป็น Go types ที่แตกต่างกัน ดังนั้น enforcer เวอร์ชัน v3 จึงต้องการ adapter release ที่ import github.com/casbin/casbin/v3 ตรวจสอบ go.mod ของ adapter:

// Example: the PostgreSQL adapter already depends on casbin/v3
import pgadapter "github.com/apache/casbin-pg-adapter"

// The file adapter is built in and ships with each major version

หาก adapter ของคุณยังไม่ได้อัปเดต ให้คงใช้ v2 สำหรับ service นั้นจนกว่าจะอัปเดต หรือเปิด issue ใน repository ของ adapter

แผนการย้อนกลับ (Rollback Plan)​

หากคุณจำเป็นต้องย้อนกลับ:

  1. ระดับโค้ด: ย้อนกลับการเปลี่ยนแปลง import (ใช้ version control)
  2. ระดับ dependency: go get github.com/casbin/casbin/v2@latest
  3. การ Deploy: ใช้กระบวนการ deployment ปกติของคุณเพื่อย้อนกลับ

ข้อดีของการย้ายระบบนี้คือ การย้อนกลับเป็นเรื่องง่ายมาก - เพียงแค่ย้อนกลับการเปลี่ยนแปลง import แล้ว deploy ใหม่

ฉันต้องย้าย Policy Database ของฉันหรือไม่?​

ไม่. ข้อมูล policy ที่มีอยู่ของคุณจะยังคงเหมือนเดิม โดย policy ถูกเก็บเป็น string ธรรมดา (subject, object, action ฯลฯ) และไม่มีการพึ่งพารุ่นของ Casbin

การทดสอบการย้ายระบบของคุณ​

การทดสอบอัตโนมัติ​

เทสต์ที่มีอยู่ของคุณควรผ่านโดยไม่ต้องแก้ไข:

func TestPolicyEnforcement(t *testing.T) {
    // This test works identically in v2 and v3
    e, _ := casbin.NewEnforcer("model.conf", "policy.csv")
    
    ok, _ := e.Enforce("alice", "data1", "read")
    if !ok {
        t.Error("Expected alice to have read access to data1")
    }
}

การทดสอบแบบ Integration​

Middleware ที่รับค่า *casbin.Enforcer จะผูกกับเวอร์ชันหลักเช่นเดียวกับ adapter หาก middleware ของคุณยัง import casbin/v2 อยู่ การเรียกใช้ enforcer โดยตรงนั้นใช้เวลาเพียงไม่กี่บรรทัด:

// Example with Gin
import (
    "net/http"

    "github.com/casbin/casbin/v3"
    "github.com/gin-gonic/gin"
)

func Authorizer(e *casbin.Enforcer) gin.HandlerFunc {
    return func(c *gin.Context) {
        ok, err := e.Enforce(c.GetString("user"), c.Request.URL.Path, c.Request.Method)
        if err != nil || !ok {
            c.AbortWithStatus(http.StatusForbidden)
            return
        }
        c.Next()
    }
}

การทดสอบโหลด (Load Testing)​

รัน load tests ปกติของคุณกับ build เวอร์ชัน v3 ลักษณะสมรรถนะควรเหมือนกันกับ v2

การตรวจสอบ Policy​

เปรียบเทียบการประเมินผล policy ข้ามเวอร์ชัน:

# Export policies from v2
# Load into v3
# Run test cases against both
# Compare results

หากคุณพบความแตกต่างใดๆ น่าจะเป็นบั๊ก กรุณาแจ้งให้ทราบ!

จุดที่ต้องระวังทั่วไป (Common Pitfalls)​

จุดที่ต้องระวังที่ 1: Mixed v2/v3 Dependencies​

ปัญหา: บาง dependencies ใช้ Casbin v2 ส่วนอื่นใช้ v3 ทำให้เกิดความขัดแย้ง

วิธีแก้: ตัว build เองไม่มีปัญหา: ระบบ module ของ Go มองว่า v2 และ v3 เป็น packages ที่แยกกัน ดังนั้นทั้งสองสามารถอยู่ใน dependency tree เดียวกันได้ สิ่งที่คุณทำไม่ได้คือการส่ง v3 enforcer ไปยัง library ที่คาดหวัง v2 enforcer ให้คง enforcer, adapter และ middleware ของมันไว้บนเวอร์ชันหลักเดียวกัน

จุดที่ต้องระวังที่ 2: Adapter Version Mismatch​

ปัญหา: การใช้ adapter เวอร์ชัน v2 กับ Casbin v3 (หรือในทางกลับกัน)

วิธีแก้: ปัญหานี้จะแสดงเป็น compile error ไม่ใช่ surprise ตอน runtime ให้ตรวจสอบว่า adapter's go.mod ต้องการ Casbin major version ใด และใช้ release ที่ตรงกับ enforcer ของคุณ

จุดที่ต้องระวังที่ 3: ลืม Internal Packages​

ปัญหา: อัปเดต imports ของแอปพลิเคชันหลักแล้ว แต่ลืม internal packages หรือ tools

วิธีแก้: ใช้ go mod graph และ go mod why เพื่อหา dependencies ของ Casbin ทั้งหมด:

go mod graph | grep casbin

จุดที่ต้องระวังที่ 4: ปัญหาการ Compile ของ Custom Adapter​

ปัญหา: Custom adapter ไม่สามารถคอมไพล์ได้หลังจากอัปเกรด

วิธีแก้ไข: อินเทอร์เฟซของ adapter ไม่ได้เปลี่ยนแปลง ดังนั้นปัญหานี้จึงชี้ไปที่ปัญหาการนำเข้า (import) ตรวจสอบว่า import ของ Casbin ทั้งหมดใน adapter ของคุณใช้ v3:

import (
    "github.com/casbin/casbin/v3"
    "github.com/casbin/casbin/v3/persist"
)

คำถามที่พบบ่อย​

ถาม: v2 ยังได้รับการดูแลอยู่หรือไม่?​

ณ เวลาที่เขียนเอกสารนี้, v2 ยังคงได้รับการแก้ไขข้อบกพร่องที่สำคัญ แต่ฟีเจอร์ใหม่จะพัฒนาสำหรับ v3 วางแผนที่จะย้ายระบบภายใน 6-12 เดือนข้างหน้า

ถาม: ฉันสามารถย้ายระบบทีละขั้นตอนโดยให้บางบริการอยู่บน v2 และอีกส่วนหนึ่งอยู่บน v3 ได้ไหม?​

ได้! พวกเขาสามารถใช้ฐานข้อมูลนโยบายเดียวกันได้ นี่เป็นหนึ่งในประโยชน์ของการเปลี่ยนแปลงที่น้อยที่สุดของ v3

ถาม: Middleware ของฉัน (Gin, Echo, Fiber ฯลฯ) จะทำงานได้หรือไม่?​

ก็ต่อเมื่อมันนำเข้าเวอร์ชันหลักเดียวกับ enforcer ของคุณ ตรวจสอบ go.mod ของ middleware; หากยังคงเป็น v2 ให้เรียก Enforce() จาก handler ขนาดเล็กของคุณเองตามที่แสดงไว้ข้างต้น

ถาม: ฉันต้องอัปเดตไฟล์โมเดล .conf ของฉันหรือไม่?​

ไม่ต้อง รูปแบบไวยากรณ์ของไฟล์โมเดลไม่มีการเปลี่ยนแปลง

ถาม: ฉันต้องอัปเดตไฟล์นโยบาย .csv ของฉันหรือไม่?​

ไม่ต้อง รูปแบบไฟล์นโยบายไม่มีการเปลี่ยนแปลง

ถาม: แล้ว WatcherEx, FilteredAdapter และอินเทอร์เฟซอื่นๆ ล่ะ?​

อินเทอร์เฟซทั้งหมดไม่มีการเปลี่ยนแปลง หากโค้ดของคุณใช้งานอินเทอร์เฟซเหล่านี้ ไม่ต้องมีการแก้ไข (นอกเหนือจากเส้นทาง import)

ถาม: มีผลกระทบต่อประสิทธิภาพหรือไม่?​

ไม่มี v3 ใช้เอนจินประเมินผลเดียวกันกับ v2

ถาม: ฉันสามารถใช้ v3 กับ Go 1.16 ได้หรือไม่?​

ตรวจสอบ go.mod ในคลังเก็บข้อมูล Casbin v3 สำหรับเวอร์ชัน Go ขั้นต่ำที่รองรับ โดยทั่วไป แนะนำให้ใช้เวอร์ชัน Go เสถียรล่าสุด
