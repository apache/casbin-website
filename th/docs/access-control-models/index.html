RBAC vs ABAC vs ACL vs ReBAC: การเลือก Access Control Model

โมเดลการควบคุมสิทธิ์ต่างกันเพียงอย่างเดียว: สิ่งที่ใช้เป็นฐานในการตัดสินใจอนุญาต

RBAC เทียบกับ ABAC แบบสั้น: RBAC มอบสิทธิ์ให้บทบาท (role) แล้วมอบบทบาทให้ผู้ใช้ จึงตอบคำถาม "บรรณาธิการทำอะไรได้บ้าง?" ได้ง่าย แต่ไม่สามารถระบุเงื่อนไข "เฉพาะเอกสารของตนเอง" โดยไม่สร้างบทบาทต่อหนึ่งเอกสาร ส่วน ABAC ประเมินเงื่อนไขจากแอตทริบิวต์ของผู้ใช้ ทรัพยากร และสภาพแวดล้อม จึงจัดการกฎเรื่องความเป็นเจ้าของ แผนก และเวลาได้เป็นธรรมชาติกว่า แต่ตรวจสอบย้อนหลัง (audit) ได้ยากกว่า แอปพลิเคชันส่วนใหญ่ใช้ RBAC สำหรับฟีเจอร์ต่างๆ และเพิ่มเงื่อนไขแบบ ABAC สำหรับบันทึกข้อมูล; ตัวอย่างสุดท้ายในหน้านี้ แสดงทั้งสองแบบในโมเดล Casbin เดียว

โมเดลตัดสินจากตัวอย่างกฎ
ACL (access control list)ผู้ใช้alice สามารถแก้ไข design.md ได้
RBAC (role-based)บทบาทของผู้ใช้บรรณาธิการสามารถแก้ไขเอกสารได้
ABAC (attribute-based)แอตทริบิวต์ของผู้ใช้ ทรัพยากร และบริบทเจ้าของสามารถแก้ไขเอกสารของตนเองได้; บุคคลในแผนกเดียวกันสามารถอ่านเอกสารได้
ReBAC (relationship-based)ความสัมพันธ์ระหว่างผู้ใช้และทรัพยากรทุกคนที่เป็นผู้ดู (viewer) ของโฟลเดอร์สามารถอ่านเอกสารภายในนั้นได้
PBAC (policy-based)นิพจน์กฎที่เก็บไว้ในรูปแบบนโยบายเงื่อนไขใดๆ ก็ตามที่แถวของนโยบายกำหนดไว้

สิ่งเหล่านี้ไม่ใช่ผลิตภัณฑ์ที่แข่งขันกัน: เป็นวิธีการเขียนกฎ และระบบจริงมักผสมผสานหลายแบบ ใน Casbin แต่ละแบบคือบรรทัดไม่กี่บรรทัดของการตั้งค่าโมเดล และคุณสามารถสลับหรือรวมมันโดยไม่ต้องเปลี่ยนโค้ดแอปพลิเคชันของคุณ หน้านี้แสดงตัวอย่างเล็กๆ เดียวกันในแต่ละโมเดล เพื่อให้เห็นความแตกต่างอย่างชัดเจน

ตัวอย่าง: แอปพลิเคชันเอกสารที่มีเอกสารหนึ่งฉบับชื่อ design.md ซึ่งเป็นของ alice. alice ควรแก้ไขได้ bob ควรอ่านได้ และไม่มีใครอื่นควรมีสิทธิ์เข้าถึง

ACL​

รายการควบคุมสิทธิ์ (Access Control List) ระบุว่าสำหรับแต่ละผู้ใช้ พวกเขาทำอะไรกับอ็อบเจกต์แต่ละชิ้นได้บ้าง

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act
p, alice, design.md, read
p, alice, design.md, edit
p, bob, design.md, read
  • จุดแข็ง: ระบบขนาดเล็กและการแชร์รายอ็อบเจกต์ ("แชร์ไฟล์นี้กับ bob") การตัดสินใจทุกอย่างเป็นเรื่องง่ายที่จะอธิบาย
  • จุดอ่อน: การขยายขนาด หากมีผู้ใช้ u คน และอ็อบเจกต์ o ชิ้น รายการจะเติบโตไปทาง u × o แถว และเมื่อมีคนเปลี่ยนงาน คุณต้องค้นหาและแก้ไขแถวทั้งหมดของพวกเขา

RBAC​

การควบคุมสิทธิ์ตามบทบาท (Role-based access control) วางบทบาทไว้ระหว่างผู้ใช้และสิทธิ์ สิทธิ์ถูกมอบให้แก่บทบาท และผู้ใช้ถูกมอบหมายบทบาท

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
p, editor, design.md, read
p, editor, design.md, edit
p, viewer, design.md, read

g, alice, editor
g, bob, viewer
g, carol, viewer

การให้ carol มีสิทธิ์อ่านทำได้ด้วยบรรทัด g เพียงบรรทัดเดียว เธอรับช่วงสิทธิ์ทุกอย่างที่ viewer ทำได้ บทบาทสามารถรับช่วงจากบทบาทอื่นได้ด้วย (g, editor, viewer) และ RBAC with domains ช่วยให้ผู้ใช้มีบทบาทต่างกันใน tenant ที่ต่างกัน

  • จุดแข็ง: สิทธิ์ที่สอดคล้องกับหน้าที่การทำงาน ตรวจสอบได้ง่าย ("บรรณาธิการทำอะไรได้บ้าง?", "ใครเป็นแอดมิน?") และการรับเข้าทำงานหรือเลิกจ้างคือการเปลี่ยนบทบาท
  • จุดอ่อน: กฎเกี่ยวกับบันทึกข้อมูลเฉพาะ "ผู้เขียนสามารถแก้ไขบทความ ของตนเอง" ไม่สามารถเขียนด้วยบทบาทเพียงอย่างเดียว; การพยายามทำเช่นนั้นนำไปสู่การสร้างบทบาทต่อหนึ่งบันทึก ซึ่งเรียกว่า role explosion

RBAC เทียบกับ ACL: ACL คือ RBAC ที่ไม่มีบทบาท เริ่มด้วย RBAC เว้นแต่ว่าคุณจะมีผู้ใช้เพียงไม่กี่คนจริงๆ เพราะการเพิ่มบทบาทในภายหลังหมายถึงการเขียนกฎใหม่ทั้งหมด

บทเรียน: Go, Node.js, NestJS, Python, Java, Rust, gRPC.

ABAC​

การควบคุมสิทธิ์ตามแอตทริบิวต์ (Attribute-based access control) ประเมินเงื่อนไขจากแอตทริบิวต์ของผู้ใช้ (แผนก ระดับความปลอดภัย) ทรัพยากร (เจ้าของ สถานะ ความละเอียดอ่อน) และสภาพแวดล้อม (เวลา IP address) ใน Casbin คุณส่งอ็อบเจกต์ไปยัง Enforce() และอ่านฟิลด์ของมันใน matcher

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = r.sub.Name == r.obj.Owner || (r.act == 'read' && r.sub.Department == r.obj.Department)

ไม่มีไฟล์นโยบาย: alice สามารถแก้ไข design.md เพราะเธอเป็นเจ้าของ และ bob สามารถอ่านได้เพราะเขาทำงานในแผนกเดียวกัน เอกสารใหม่ในแผนกออกแบบสามารถอ่านโดย bob ได้โดยไม่ต้องเปลี่ยนแปลงกฎใดๆ

  • จุดแข็ง: กฎที่ขึ้นอยู่กับบันทึกข้อมูลหรือบริบท: ความเป็นเจ้าของ แผนก สถานะเอกสาร เวลาทำการ ภูมิภาค กฎหนึ่งข้อแทนที่การมอบบทบาทจำนวนมาก
  • จุดอ่อน: การตรวจสอบย้อนหลัง คำถาม "ใครสามารถอ่านเอกสารนี้ได้บ้าง?" ไม่มีคำตอบโดยตรง; คุณต้องประเมินเงื่อนไขเทียบกับผู้ใช้ทุกคน นอกจากนี้เงื่อนไขยังต้องมีแอตทริบิวต์พร้อมใช้งาน ซึ่งหมายความว่าต้องโหลดบันทึกข้อมูลก่อนการตรวจสอบ

ด้วย eval() pattern เงื่อนไขจะถูกย้ายจากโมเดลไปอยู่ในแถวของนโยบาย ดังนั้นจึงสามารถเพิ่มและลบได้ในช่วงรันไทม์เหมือนกฎอื่นๆ

บทเรียน: Go, Node.js with Express, Python with Flask.

ReBAC​

การควบคุมสิทธิ์ตามความสัมพันธ์ (Relationship-based access control) ได้สิทธิ์มาจากความสัมพันธ์: alice เป็น owner ของ design.md, bob เป็น viewer ของมัน และ owners สามารถแก้ไขขณะที่ viewers สามารถอ่าน นี่คือโมเดลเบื้องหลัง Google Zanzibar และโครงการโอเพนซอร์สที่ต่อยอดมา

[request_definition]
r = sub, obj, act

[policy_definition]
p = relation, obj_type, act

[role_definition]
g = _, _, _
g2 = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, r.obj, p.relation) && g2(r.obj, p.obj_type) && r.act == p.act
p, owner, doc, read
p, owner, doc, edit
p, viewer, doc, read

g, alice, design.md, owner
g, bob, design.md, viewer
g, bob, roadmap.md, owner

g2, design.md, doc
g2, roadmap.md, doc

bob สามารถแก้ไข roadmap.md ซึ่งเป็นของเขาเอง แต่สามารถอ่าน design.md ได้เท่านั้น กฎ p อธิบายว่าแต่ละความสัมพันธ์อนุญาตอะไรได้บ้างสำหรับประเภทอ็อบเจกต์ทั้งหมด และแถว g บันทึกว่าใครมีความสัมพันธ์ใดกับอ็อบเจกต์ไหน

  • จุดแข็ง: การแชร์และความร่วมมือ (เอกสาร โฟลเดอร์ โปรเจกต์ องค์กร) โดยเฉพาะอย่างยิ่งเมื่อสิทธิ์ถูกรับช่วงผ่านลำดับชั้น เช่น organization → folder → document
  • จุดอ่อน: ระบบขนาดเล็กหรือแบนราบ ซึ่งต้องใช้กลไกเกินจำเป็น ความสัมพันธ์ต้องถูกเขียนขึ้นทุกครั้งที่มีการสร้างหรือแชร์อ็อบเจกต์

ดูที่ ReBAC สำหรับโมเดลเต็ม และ Casbin vs. OpenFGA หากคุณกำลังพิจารณาสไตล์บริการ Zanzibar โดยเฉพาะ

PBAC​

การควบคุมสิทธิ์ตามนโยบาย (Policy-based access control) ไม่ใช่โมเดลแยกต่างหากเท่ากับการเขียนโมเดลอื่นๆ อีกวิธีหนึ่ง: ตัวกฎเองเป็นนิพจน์ที่เก็บในรูปแบบนโยบายและประเมินผลในช่วงรันไทม์ ใน Casbin นั่นคือ eval() pattern ที่ใช้ในบทเรียน ABAC และหน้า PBAC จุดเด่นคือด้านปฏิบัติการ: ทีมรักษาความปลอดภัยหรือทีมปฏิบัติตามข้อกำหนดสามารถเปลี่ยนกฎได้โดยไม่ต้องปล่อยเวอร์ชันโค้ดใหม่

บริบท (เวลา, IP, สถานะ)ไม่ได้ไม่ได้ได้ได้เฉพาะเมื่อมีเงื่อนไขเพิ่มเติม
การใช้งานทั่วไปเครื่องมือขนาดเล็ก, การแชร์ไฟล์แผงผู้ดูแลระบบ, เครื่องมือภายใน, แอปพลิเคชันธุรกิจส่วนใหญ่แพลตฟอร์มข้อมูล, ข้อมูลที่มีกฎระเบียบ, กฎความเป็นเจ้าของแอปพลิเคชันทำงานร่วมกัน, โครงสร้างลำดับชั้นหลายระดับ

วิธีการเลือก​

  1. เริ่มด้วย RBAC หากสิทธิ์สามารถอธิบายได้ตามหน้าที่งาน ("admins", "editors", "billing") RBAC คือโมเดลที่เรียบง่ายที่สุดที่ขยายขนาดได้และตรวจสอบได้ง่ายที่สุด
  2. เพิ่มเงื่อนไข ABAC สำหรับความเป็นเจ้าของและบริบท เมื่อคุณพบว่าต้องการ "เฉพาะของตนเอง" หรือ "เฉพาะในเวลาทำการ" ให้เพิ่มเงื่อนไขแทนการสร้างบทบาทใหม่
  3. เลือก ReBAC เมื่อการแชร์คือจุดขายของผลิตภัณฑ์ หากผู้ใช้แชร์วัตถุระหว่างกันและการเข้าถึงส่งผ่านไปยังโฟลเดอร์ โปรเจกต์ หรือองค์กร ให้จำลองความสัมพันธ์โดยตรง
  4. ใช้โดเมนสำหรับมัลติเทนนซี หากผู้ใช้คนเดียวกันมีบทบาทต่างกันในองค์กรต่างๆ ให้ใช้ RBAC with domains ไม่ว่าคุณจะเลือกโมเดลอื่นอย่างไรก็ตาม
  5. พิจารณาโมเดลบังคับใช้เฉพาะเมื่อจำเป็นเท่านั้น BLP, Biba, และ LBAC เหมาะกับสภาพแวดล้อมที่มีระดับชั้นความลับ เช่น ภาครัฐหรือกลาโหม

การรวม RBAC และ ABAC​

แอปพลิเคชันส่วนใหญ่จะจบลงที่นี่: บทบาทกำหนดว่าฟีเจอร์ใดที่ผู้ใช้เข้าถึงได้ และแอตทริบิวต์จำกัดขอบเขตนั้นให้เหลือเฉพาะรายการที่พวกเขาอาจแตะต้อง ในโมเดลนี้ ผู้ดูแลระบบอาจแก้ไขเอกสารใดๆ ก็ได้ ในขณะที่ผู้เขียนอาจแก้ไขเฉพาะเอกสารที่เป็นเจ้าของเท่านั้น:

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub.Name, p.sub) && r.obj.Type == p.obj && r.act == p.act && (p.sub == 'admin' || r.sub.Name == r.obj.Owner)
p, admin, doc, edit
p, author, doc, edit

g, erin, admin
g, alice, author
g, bob, author

สำหรับ design.md (type doc, owner alice), alice อาจแก้ไขได้เพราะเธอเป็นผู้เขียนและเป็นเจ้าของ, erin อาจแก้ไขได้เพราะเธอเป็นผู้ดูแลระบบ, และ bob อาจไม่ได้: เขาเป็นผู้เขียน แต่ไม่ใช่เจ้าของ

คำถามที่พบบ่อย​

ความแตกต่างระหว่าง RBAC และ ABAC คืออะไร? RBAC กำหนดสิทธิ์ให้กับบทบาท (roles) และมอบหมายบทบาทให้ผู้ใช้ ดังนั้นจึงตอบคำถาม "บรรณาธิการทำอะไรได้บ้าง?" ส่วน ABAC ประเมินเงื่อนไขจากแอตทริบิวต์ของผู้ใช้ ทรัพยากร และสภาพแวดล้อม ดังนั้นจึงตอบคำถาม "ผู้ใช้คนนี้แก้ไขระเบียนนี้ได้ ณ ขณะนี้หรือไม่?" RBAC ตรวจสอบได้ง่ายกว่า ในขณะที่ ABAC สามารถแสดงกฎเกี่ยวกับความเป็นเจ้าของ แผนก และเวลา โดยไม่ต้องสร้างบทบาทสำหรับแต่ละระเบียน แอปพลิเคชันส่วนใหญ่ใช้บทบาทสำหรับฟีเจอร์ต่างๆ และใช้เงื่อนไขของแอตทริบิวต์สำหรับระเบียน ดังเช่นตัวอย่างรวมที่กล่าวถึงข้างต้น

ABAC ปลอดภัยกว่า RBAC หรือไม่? ไม่มีอันไหนปลอดภัยกว่าโดยเนื้อแท้ ABAC สามารถแสดงกฎที่ละเอียดกว่าได้ แต่การตัดสินใจของมันตรวจสอบได้ยากกว่า; RBAC หยาบกว่าแต่ตรวจสอบง่าย ความปลอดภัยมาจากกฎที่ตรงกับสิ่งที่คุณตั้งใจ และจากความสามารถในการตรวจสอบว่ามันตรงจริงหรือไม่

ฉันสามารถเริ่มด้วย RBAC แล้วเปลี่ยนไปใช้ ABAC ทีหลังได้ไหม? ได้ ใน Casbin โมเดลเป็นไฟล์คอนฟิกูเรชัน และแอปพลิเคชันเรียกเมธอด Enforce() เดิม ดังนั้นคุณสามารถเพิ่มเงื่อนไขลงใน matcher หรือรวมทั้งสองแบบดังที่แสดงข้างต้น โดยไม่ต้องเขียนโค้ดการอนุญาตใหม่

PBAC อยู่ตรงไหน? PBAC อธิบาย วิธี จัดการกฎ (เป็นข้อมูลนโยบายที่ประเมินตอนรันไทม์) มากกว่า สิ่งที่ กฎเหล่านั้นอิงอยู่ นโยบายของ Casbin เป็นข้อมูลในทุกโมเดล ดังนั้นโมเดลข้างต้นใดๆ ก็ตามสามารถจัดการด้วยวิธีนี้ได้

ไลบรารีและแพลตฟอร์มใดรองรับทั้ง RBAC และ ABAC? Casbin รองรับทั้งสองแบบ และการผสมผสานของพวกเขา ในโมเดลเดียวสำหรับ Go, Java, Node.js, Python, .NET, Rust และภาษาอื่นๆ เอนจินนโยบายเช่น OPA และ Cedar สามารถแสดงทั้งสองแบบได้เช่นกัน ในขณะที่บริการสไตล์ Zanzibar เช่น OpenFGA ถูกสร้างขึ้นรอบๆ ReBAC Casbin vs. Alternatives เปรียบเทียบพวกมัน

Casbin รองรับทั้งหมดเหล่านี้หรือไม่? ใช่ รวมถึงอันอื่นๆ เช่น RBAC96, OrBAC, UCON, LBAC, โมเดลความสมบูรณ์ Biba และนโยบายแบบ priority และ deny-override ดูที่ Supported models และลองใช้โมเดลใดก็ได้ใน online editor Super administrators ถูกจัดการด้วยเงื่อนไข matcher เพิ่มเติมหนึ่งข้อ แทนที่จะเป็นโมเดลแยกต่างหาก
