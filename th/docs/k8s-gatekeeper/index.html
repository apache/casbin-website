**Kubernetes Admission Webhook**

ภาพรวม​

Casbin K8s-Gatekeeper เป็น admission webhook ของ Kubernetes ที่ใช้ Casbin สำหรับการจัดการสิทธิ์การใช้งาน คุณสามารถกำหนดโมเดลและนโยบายแบบ declarative เพื่ออนุญาตหรือปฏิเสธการดำเนินการกับทรัพยากร Kubernetes ใดๆ ได้ โดยไม่ต้องเขียนโค้ดปรับแต่งเองใน webhook ดูแลรักษาโดยชุมชน Casbin: github.com/apache/casbin-k8s-gatekeeper

ตัวอย่างพื้นฐาน​

ตัวอย่าง: ปฏิเสธ deployments ที่ใช้อิมเมจที่มี tag เฉพาะ โดยใช้เพียงการตั้งค่า:

โมเดล:

[request_definition]
r =  obj

[policy_definition]
p =  obj,eft

[policy_effect]
e = !some(where (p.eft == deny))

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
contain(split(accessWithWildcard(${OBJECT}.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj)

นโยบาย:

p, "1.14.1",deny

ตัวอย่างนี้ใช้ภาษา ACL มาตรฐานของ Casbin ซึ่งควรเข้าใจได้ง่ายหากคุณได้อ่านบทนำมาก่อนแล้ว

Casbin K8s-Gatekeeper มีข้อดีหลายประการ:

  • ใช้งานง่าย—เขียนการตั้งค่า ACL แทนการเขียนโค้ดจำนวนมาก
  • รองรับการอัปเดตการตั้งค่าแบบเรียลไทม์โดยไม่ต้องรีสตาร์ทปลั๊กอิน
  • มีความยืดหยุ่น—ใช้กฎที่กำหนดเองกับทรัพยากร Kubernetes ใดก็ได้โดยใช้ kubectl gatekeeper
  • ช่วยลดความซับซ้อนในการติดตั้ง Kubernetes admission webhook—ไม่จำเป็นต้องเข้าใจกลไกภายในของ webhook หรือเขียนโค้ด webhook เพียงกำหนดข้อจำกัดและเขียน Casbin ACL
  • ดูแลรักษาโดยชุมชน—ติดต่อเราหากมีคำถามหรือปัญหา

1.1 วิธีทำงานของ Casbin K8s-Gatekeeper​

K8s-Gatekeeper เป็น admission webhook สำหรับ Kubernetes ที่ใช้ Casbin เพื่อบังคับใช้กฎการควบคุมการเข้าถึงที่กำหนดเอง ป้องกันการดำเนินการที่ไม่พึงประสงค์บนทรัพยากร Kubernetes

Casbin เป็นไลบรารีควบคุมการเข้าถึงแบบโอเพนซอร์สที่มีประสิทธิภาพ รองรับโมเดลการจัดการสิทธิ์การใช้งานที่หลากหลาย สำหรับรายละเอียดเพิ่มเติม ดูที่ ภาพรวม

Admission webhooks ใน Kubernetes คือ HTTP callbacks ที่รับและประมวลผลคำขอ admission K8s-Gatekeeper เป็น ValidatingAdmissionWebhook ที่ยอมรับหรือปฏิเสธคำขอ admission คำขอ admission คือคำขอ HTTP ที่อธิบายการดำเนินการกับทรัพยากร Kubernetes (เช่น การสร้างหรือลบ deployment) สำหรับข้อมูลเพิ่มเติม ดูที่ เอกสารประกอบ Kubernetes

1.2 ตัวอย่างขั้นตอนการทำงาน​

เมื่อมีคนสร้าง deployment ที่มี nginx pod (ผ่าน kubectl หรือ clients ของ Kubernetes) Kubernetes จะสร้างคำขอ admission ดังนี้ (ในรูปแบบ YAML):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  selector:
    matchLabels:
      app: nginx
  replicas: 1
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.1
        ports:
        - containerPort: 80

คำขอนี้จะผ่านชั้น middleware รวมถึง K8s-Gatekeeper K8s-Gatekeeper จะตรวจจับ enforcers ของ Casbin ทั้งหมดที่เก็บไว้ใน etcd ของ Kubernetes (ซึ่งผู้ใช้สร้างและดูแลรักษาผ่าน kubectl หรือ Go client ที่จัดให้) แต่ละ enforcer ประกอบด้วยโมเดลและนโยบายของ Casbin คำขอ admission จะถูกประเมินโดยแต่ละ enforcer ตามลำดับ และต้องผ่านทุก enforcer จึงจะได้รับการยอมรับ

(หากคุณไม่คุ้นเคยกับ enforcers, โมเดล หรือนโยบายของ Casbin ดูที่ เริ่มต้นใช้งาน)

ตัวอย่างเช่น หากผู้ดูแลระบบต้องการบล็อกอิมเมจ 'nginx:1.14.1' ขณะที่อนุญาต 'nginx:1.3.1' พวกเขาสามารถสร้าง enforcer พร้อมโมเดลและนโยบายนี้ได้ (รายละเอียดการสร้างและการกำหนดค่าจะมีในหัวข้อถัดไป):

โมเดล:

[request_definition]
r =  obj

[policy_definition]
p =  obj,eft

[policy_effect]
e = !some(where (p.eft == deny))

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") == p.obj

นโยบาย:

p, "nginx:1.13.1",allow
p, "nginx:1.14.1",deny

การสร้าง enforcer ด้วยโมเดลและนโยบายนี้จะปฏิเสธคำขอ admission ป้องกันไม่ให้ Kubernetes สร้าง deployment

2. การติดตั้ง K8s-gatekeeper​

มีวิธีการติดตั้ง 3 แบบ: External webhook, Internal webhook และ Helm

หมายเหตุ

วิธีการติดตั้งเหล่านี้มีไว้เพื่อวัตถุประสงค์ในการประเมินเท่านั้น สำหรับการติดตั้งในระบบจริง โปรดตรวจสอบ บทที่ 5. การตั้งค่าขั้นสูง และทำการแก้ไขด้านความปลอดภัยที่จำเป็นก่อนการติดตั้ง

2.1 Internal Webhook​

2.1.1 ขั้นตอนที่ 1: สร้าง Image​

สำหรับการติดตั้งแบบ internal webhook, K8s-gatekeeper จะทำงานเป็นบริการ Kubernetes สร้าง image:

docker build --target webhook -t k8s-gatekeeper .

สิ่งนี้จะสร้าง image ในเครื่องชื่อ 'k8s-gatekeeper:latest'

หมายเหตุ

สำหรับผู้ใช้ minikube ให้รัน eval $(minikube -p minikube docker-env) ก่อนคำสั่ง 'docker build'

2.1.2 ขั้นตอนที่ 2: ติดตั้ง Services และ Resources​

รันคำสั่งเหล่านี้:

kubectl apply -f config/rbac.yaml
kubectl apply -f config/webhook_deployment.yaml 
kubectl apply -f config/webhook_internal.yaml

ตรวจสอบการติดตั้งด้วย kubectl get pods

2.1.3 ขั้นตอนที่ 3: ติดตั้ง CRD Resources​

ติดตั้ง custom resource definitions:

kubectl apply -f config/auth.casbin.org_casbinmodels.yaml 
kubectl apply -f config/auth.casbin.org_casbinpolicies.yaml

2.2 External Webhook​

สำหรับการติดตั้งแบบ external webhook, K8s-gatekeeper จะทำงานอยู่นอก Kubernetes Kubernetes ต้องการ HTTPS สำหรับ admission webhooks เราจัดหาใบรับรองทดสอบและ private key ให้ (ไม่ปลอดภัยสำหรับระบบจริง) สำหรับใบรับรองที่กำหนดเอง ดูที่ บทที่ 5. การตั้งค่าขั้นสูง

ใบรับรองที่ระบุออกสำหรับ 'webhook.domain.local' อัปเดตไฟล์ hosts ของคุณ (เช่น /etc/hosts) เพื่อชี้ 'webhook.domain.local' ไปยังที่อยู่ IP ที่ K8s-gatekeeper ทำงานอยู่

รัน:

go mod tidy
go mod vendor
go run cmd/webhook/main.go
kubectl apply -f config/auth.casbin.org_casbinmodels.yaml 
kubectl apply -f config/auth.casbin.org_casbinpolicies.yaml
kubectl apply -f config/webhook_external.yaml

2.3 การติดตั้งผ่าน Helm​

2.3.1 ขั้นตอนที่ 1: สร้าง Image​

ดู บทที่ 2.1.1

2.3.2 การติดตั้งด้วย Helm​

รัน: helm install k8sgatekeeper ./k8sgatekeeper

3. การใช้ K8s-gatekeeper​

3.1 การสร้าง Casbin Models และ Policies​

สร้าง models และ policies โดยใช้ kubectl หรือ Go client ที่จัดเตรียมไว้ให้

3.1.1 สร้าง/อัปเดตผ่าน kubectl​

ใน K8s-gatekeeper, Casbin models ถูกเก็บเป็นทรัพยากร CRD ประเภท 'CasbinModel' โดยนิยามอยู่ใน config/auth.casbin.org_casbinmodels.yaml

ดูตัวอย่างใน example/allowed_repo/model.yaml ฟิลด์สำคัญ:

  • metadata.name: ชื่อ Model ต้องตรงกับชื่อของวัตถุ CasbinPolicy ที่เกี่ยวข้อง เพื่อให้ K8s-gatekeeper จับคู่ได้อย่างถูกต้อง
  • spec.enable: ตั้งค่าเป็น "false" เพื่อปิดใช้งาน model นี้และ policy ที่เกี่ยวข้อง
  • spec.modelText: สตริงที่มีนิยามของ Casbin model

Casbin policies ถูกเก็บเป็นทรัพยากร CRD ประเภท 'CasbinPolicy' โดยนิยามอยู่ใน config/auth.casbin.org_casbinpolicies.yaml

ดูตัวอย่างใน example/allowed_repo/policy.yaml ฟิลด์สำคัญ:

  • metadata.name: ชื่อ Policy ต้องตรงกับชื่อของวัตถุ CasbinModel ที่เกี่ยวข้อง
  • spec.policyItem: สตริงที่มีนิยามของ Casbin policy

ใช้ไฟล์ CasbinModel และ CasbinPolicy ของคุณ:

kubectl apply -f <filename>

K8s-gatekeeper จะตรวจจับคู่ของ CasbinModel/CasbinPolicy ใหม่ภายใน 5 วินาที

3.1.2 สร้าง/อัปเดตผ่าน Go Client​

สำหรับสถานการณ์ที่ไม่สามารถเข้าถึง shell บนโหนดคลัสเตอร์โดยตรงได้ (เช่น เมื่อสร้างแพลตฟอร์มคลาวด์อัตโนมัติ) เรามี Go client สำหรับจัดการทรัพยากร CasbinModel และ CasbinPolicy

ไลบรารี Go client อยู่ใน pkg/client

ใน client.go ใช้ฟังก์ชันนี้เพื่อสร้าง client:

func NewK8sGateKeeperClient(externalClient bool) (*K8sGateKeeperClient, error)

พารามิเตอร์ externalClient บ่งบอกว่า K8s-gatekeeper ทำงานภายในหรือภายนอก Kubernetes cluster

ใน model.go มีฟังก์ชันสำหรับการสร้าง ลบ และแก้ไข CasbinModel ดูตัวอย่างการใช้งานใน model_test.go

ใน policy.go มีฟังก์ชันสำหรับการสร้าง ลบ และแก้ไข CasbinPolicy ดูตัวอย่างการใช้งานใน policy_test.go

3.1.2 การทดสอบ K8s-gatekeeper​

หลังจากสร้าง model และ policy จาก example/allowed_repo ให้ทดสอบโดย:

kubectl apply -f example/allowed_repo/testcase/reject_1.yaml

Kubernetes ควรปฏิเสธคำขอนี้ โดยระบุว่า webhook เป็นเหตุผลในการปฏิเสธ อย่างไรก็ตาม การนำ example/allowed_repo/testcase/approve_2.yaml มาใช้ควรสำเร็จ

4. การเขียน Models และ Policies สำหรับ K8s-gatekeeper​

ตรวจสอบให้แน่ใจว่าคุณเข้าใจไวยากรณ์ของ Casbin model และ policy ก่อนดำเนินการต่อ หากยังไม่เข้าใจ โปรดอ่านหัวข้อ Get Started ก่อน บทนี้สมมติว่าคุณคุ้นเคยกับ Casbin models และ policies แล้ว

4.1 นิยาม Request​

เมื่อ K8s-gatekeeper ประเมินคำขอ ข้อมูลนำเข้าจะเป็นวัตถุ Go ประเภท AdmissionReview เสมอ โดยใช้งาน enforcer ดังนี้:

ok, err := enforcer.Enforce(admission)

โดยที่ admission คือวัตถุ AdmissionReview จาก API Go อย่างเป็นทางการของ Kubernetes "k8s.io/api/admission/v1" โครงสร้างข้อมูลมีรายละเอียดอยู่ที่: https://github.com/kubernetes/api/blob/master/admission/v1/types.go เอกสารเพิ่มเติม: https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#webhook-request-and-response

สำหรับโมเดลของ K8s-gatekeeper ส่วน request_definition ควรปฏิบัติตามรูปแบบนี้เสมอ:

    [request_definition]
    r =  obj

ชื่อ 'obj' สามารถเปลี่ยนได้ตราบใดที่ใช้สอดคล้องกันในส่วน [matchers]

4.2 Model Matchers​

ใช้ฟีเจอร์ ABAC ของ Casbin เพื่อเขียนกฎ อย่างไรก็ตาม ตัวประเมินนิพจน์ของ Casbin ไม่รองรับการระบุตำแหน่งใน map/array หรือการขยาย array โดยธรรมชาติ K8s-gatekeeper มีฟังก์ชันส่วนขยายเพื่อแก้ไขปัญหานี้ หากคุณต้องการฟังก์ชันเพิ่มเติม กรุณาเปิด issue หรือส่ง pull request

สำหรับข้อมูลเบื้องหลังเกี่ยวกับฟังก์ชันของ Casbin ดูที่ Function

ฟังก์ชันส่วนขยาย:

4.2.1 ฟังก์ชันส่วนขยาย​

4.2.1.1 access​

ฟังก์ชัน access ช่วยให้คุณสามารถระบุตำแหน่งใน map และ array ได้ ดูตัวอย่างที่ example/allowed_repo/model.yaml:

[matchers]
m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") == p.obj

ในกรณีนี้ access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Image") เทียบเท่ากับการเขียนเป็น r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Image ซึ่ง r.obj.Request.Object.Object.Spec.Template.Spec.Containers เป็น slice

นอกจากนี้ access ยังสามารถใช้เรียกฟังก์ชันที่ไม่รับพารามิเตอร์และคืนค่าเดียวได้ ดูตัวอย่างที่ example/container_resource_limit/model.yaml:

[matchers]
  m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
  parseFloat(access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","cpu","Value")) >= parseFloat(p.cpu) && \
  parseFloat(access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","memory","Value")) >= parseFloat(p.memory)

ในกรณีนี้ access(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , 0, "Resources","Limits","cpu","Value") เท่ากับ r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Resources.Limits["cpu"].Value() ซึ่ง r.obj.Request.Object.Object.Spec.Template.Spec.Containers[0].Resources.Limits เป็น map และ Value() เป็นฟังก์ชันที่ไม่รับพารามิเตอร์และคืนค่าเดียว

4.2.1.2 accessWithWildcard​

เพื่อตรวจสอบเงื่อนไขทั่วทั้งองค์ประกอบของ array (เช่น "ทุกองค์ประกอบต้องขึ้นต้นด้วย 'aaa'") โดยไม่ต้องใช้ลูป for ให้ใช้ accessWithWildcard ร่วมกับการขยาย map/slice

หาก a.b.c คือ array [aaa,bbb,ccc,ddd,eee] ดังนั้น accessWithWildcard(a,"b","c","*") จะคืนค่า slice [aaa,bbb,ccc,ddd,eee] โดย wildcard * จะทำหน้าที่ขยาย slice

รองรับการใช้ wildcard หลายตัว ตัวอย่างเช่น accessWithWildcard(a,"b","c","*","*") จะคืนค่า [a.b.c[0][0], a.b.c[0][1], ..., a.b.c[1][0], a.b.c[1][1], ...]

4.2.1.3 ฟังก์ชันแบบ Argument ยืดหยุ่น (Variable-Length Argument Functions)​

ตัวประเมินนิพจน์ของ Casbin จะทำการขยาย array เป็น argument แบบยืดหยุ่นโดยอัตโนมัติ โดยใช้ประโยชน์จากกลไกนี้สำหรับการขยาย array/slice/map ฟังก์ชันหลายตัวจึงสามารถรับ array/slice ได้ดังนี้:

  • contain(): รับพารามิเตอร์หลายตัวและคืนค่าว่าพารามิเตอร์ใด ๆ (ยกเว้นตัวสุดท้าย) มีค่าเท่ากับพารามิเตอร์ตัวสุดท้ายหรือไม่
  • split(a,b,c...,sep,index): คืนค่า [splits(a,sep)[index], splits(b,sep)[index], splits(c,sep)[index], ...]
  • len(): คืนจำนวนของ argument แบบยืดหยุ่น
  • matchRegex(a,b,c...,regex): คืนค่าว่าพารามิเตอร์ทั้งหมด (a, b, c, ...) ตรงกับ regex หรือไม่

ตัวอย่างจาก example/disallowed_tag/model.yaml:

    [matchers]
    m = r.obj.Request.Namespace == "default" && r.obj.Request.Resource.Resource =="deployments" && \
    contain(split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj)

หาก accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image") คืนค่า ["a:b", "c:d", "e:f", "g:h"] การดำเนินการ split จะประมวลผลแต่ละองค์ประกอบพร้อมรองรับ argument แบบยืดหยุ่น โดยเลือก index ที่ 1 จากแต่ละรายการ ดังนั้น split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) จะคืนค่า ["b","d","f","h"] สุดท้าย contain(split(accessWithWildcard(r.obj.Request.Object.Object.Spec.Template.Spec.Containers , "*", "Image"),":",1) , p.obj) จะตรวจสอบว่ามี p.obj อยู่ใน ["b","d","f","h"] หรือไม่

4.2.1.2 ฟังก์ชันแปลงชนิดข้อมูล (Type Conversion Functions)​

  • ParseFloat(): แปลงจำนวนเต็มเป็นทศนิยม (จำเป็นเนื่องจากการเปรียบเทียบต้องใช้ชนิดข้อมูล float)
  • ToString(): แปลงอ็อบเจกต์เป็นสตริง อ็อบเจกต์นั้นต้องมีชนิดพื้นฐานเป็น string (เช่น type XXX string)
  • IsNil(): คืนค่าว่าพารามิเตอร์มีค่าเป็น nil หรือไม่

5. การตั้งค่าขั้นสูง​

5.1 การกำหนดค่าใบรับรอง​

Kubernetes กำหนดให้ webhook ต้องใช้งานผ่าน HTTPS โดยมีตัวเลือกสองแบบ:

  • ใบรับรองที่ออกเอง (Self-signed certificates) (ใช้ในตัวอย่างของ repository นี้)
  • ใบรับรองที่ได้รับความไว้วางใจจากสาธารณะ (Publicly trusted certificates)

5.1.1 ใบรับรองที่ออกเอง (Self-Signed Certificates)​

ใบรับรองที่ออกเองจะใช้ Certificate Authority (CA) ที่ไม่ได้รับการยอมรับจากสาธารณะ คุณจึงต้องกำหนดค่าให้ Kubernetes ไว้วางใจ CA นี้

ตัวอย่างใน repository ใช้ CA ที่กำหนดเองซึ่งเก็บคีย์ส่วนตัวและใบรับรองไว้ใน config/certificate/ca.key และ config/certificate/ca.crt ใบรับรองของ webhook config/certificate/server.crt ออกโดย CA นี้สำหรับโดเมน "webhook.domain.local" (external webhook) และ "casbin-webhook-svc.default.svc" (internal webhook)

ข้อมูล CA ถูกส่งไปยัง Kubernetes ผ่านไฟล์กำหนดค่า webhook ทั้ง config/webhook_external.yaml และ config/webhook_internal.yaml มีฟิลด์ "CABundle" ซึ่งเก็บใบรับรอง CA ที่เข้ารหัสแบบ base64

หากต้องการเปลี่ยนใบรับรองหรือโดเมน (เช่น ย้าย webhook ไปยัง namespace อื่นหรือเปลี่ยนโดเมน):

  1. สร้าง CA ใหม่:

    • สร้างคีย์ส่วนตัวของ CA:

      openssl genrsa -des3 -out ca.key 2048

    • ลบการป้องกันด้วยรหัสผ่าน:

      openssl rsa -in ca.key -out ca.key

  2. สร้างคีย์ส่วนตัวของเซิร์ฟเวอร์ webhook:

    openssl genrsa -des3 -out server.key 2048
    openssl rsa -in server.key -out server.key

  3. ลงนามใบรับรอง webhook ด้วย CA:

    • คัดลอกไฟล์ config OpenSSL ของระบบคุณ (ค้นหาด้วย openssl version -a โดยทั่วไปคือ openssl.cnf)

    • แก้ไขไฟล์ config:

      • ในส่วน [req] ให้เพิ่ม: req_extensions = v3_req

      • ในส่วน [v3_req] ให้เพิ่ม: subjectAltName = @alt_names

      • ต่อท้ายด้วย:

        [alt_names]
        DNS.2=<Your desired domain>

        หมายเหตุ: แทนที่ 'casbin-webhook-svc.default.svc' ด้วยชื่อ service จริงของคุณหากมีการเปลี่ยนแปลง

    • สร้าง certificate request:

      openssl req -new -nodes -keyout server.key -out server.csr -config openssl.cnf

    • ลงนาม certificate ด้วย CA:

      openssl x509 -req -days 3650 -in server.csr -out server.crt -CA ca.crt -CAkey ca.key -CAcreateserial -extensions v3_req -extensions SAN -extfile openssl.cnf

  4. อัปเดตฟิลด์ 'CABundle' ในทั้ง config/webhook_external.yaml และ config/webhook_internal.yaml ด้วยใบรับรอง CA ใหม่ที่เข้ารหัสแบบ base64

  5. สำหรับการติดตั้งด้วย Helm ให้ใช้การเปลี่ยนแปลงที่เทียบเท่ากันกับ Helm charts

5.1.2 ใบรับรองที่ได้รับความไว้วางใจจากสาธารณะ​

เมื่อใช้ใบรับรองที่ได้รับความไว้วางใจจากสาธารณะ ให้ข้ามขั้นตอนข้างต้น ลบฟิลด์ "CABundle" ออกจาก config/webhook_external.yaml และ config/webhook_internal.yaml และตั้งค่าโดเมนเป็นโดเมนที่คุณลงทะเบียนไว้
