Що таке RBAC? Role-Based Access Control із прикладами

Що таке RBAC?​

Role-based access control (RBAC) надає дозволи ролям, а не окремим користувачам, і призначає кожному користувачеві одну або кілька ролей. Щоб дозволити новому співробітнику виконувати свою роботу, ви призначаєте їм роль, наприклад editor або billing; щоб змінити те, що можуть робити всі редактори, ви змінюєте роль лише один раз.

RBAC складається з трьох частин:

  • Користувачі: люди або сервіси, які надсилають запити.
  • Ролі: іменовані функціональні обов’язки, такі як admin, editor або viewer.
  • Дозволи: дія щодо ресурсу, наприклад edit для /articles.

Запит дозволено, якщо одна з ролей користувача має відповідний дозвіл. Ролі також можуть спадковуватися від інших ролей: якщо editor спадкує від viewer, редактори отримують усі можливості глядачів. Концепцію RBAC формалізував NIST у 1990-х роках, а сімейство моделей RBAC96 описує варіанти: плоскі ролі, ієрархії ролей та обмеження. Див. RBAC vs. RBAC96, щоб дізнатися, як Casbin відповідає цим моделям.

Мінімальна модель RBAC та політика в Casbin:

[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
p, editor, article, edit
p, viewer, article, read

g, editor, viewer
g, alice, editor
g, bob, viewer

alice може редагувати та читати статті (editor успадковує viewer); bob може лише читати їх.

RBAC проти ABAC​

RBAC is easy to audit but cannot say "only their own records" without creating a role per record. ABAC adds conditions on attributes such as the owner or the time of day, and most applications combine both. Choosing an access control model compares ACL, RBAC, ABAC and ReBAC on one example.

Навчальні посібники: додайте RBAC до веб-API в Go з Gin, Node.js з Express, NestJS, Python з FastAPI, Java зі Spring Boot, Rust або gRPC. Також можна спробувати приклади RBAC в онлайн-редакторі.

Визначення ролей​

Секція [role_definition] визначає зв’язки ролей RBAC (спадкування). Casbin може одночасно використовувати кілька систем RBAC: одну для користувачів (зі спадкуванням ролей) і, за бажанням, одну для ресурсів. Кожна з них є незалежною.

Ця секція є необов’язковою; пропустіть її, якщо ви не використовуєте RBAC.

[role_definition]
g = _, _
g2 = _, _

Тут g та g2 — це дві системи ролей; _, _ означає, що кожна з них має дві сторони (наприклад, користувач і роль). Використовуйте лише g для ролей користувачів; додайте g2, якщо ресурси також мають ролі. Приклади: rbac_model.conf, rbac_with_resource_roles_model.conf.

Відповідності між користувачами та ролями (і між ресурсами та ролями) зберігаються в політиці, наприклад:

p, data2_admin, data2, read
g, alice, data2_admin

Отже, alice має роль data2_admin. Casbin розглядає всі назви як рядки (користувач, ресурс або роль).

Використовуйте роль у matcher:

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act

Таким чином, запит дозволяється лише тоді, коли суб’єкт запиту має роль, зазначену в політиці.

примітка
  1. Casbin лише зберігає та оцінює відповідності між користувачами та ролями (і між ресурсами та ролями); він не перевіряє наявність користувачів чи ролей. Це завдання автентифікації.
  2. Do not reuse the same name for a user and a role (e.g. user alice and role alice), since Casbin cannot tell them apart. Use typed names to keep them apart.
  3. Спадкування ролей є транзитивним і необмеженим: якщо A має роль B, а B має роль C, то фактично A має роль C.
Конвенція іменування токенів

Суб’єкт у політиці зазвичай називається sub і перелічується першим. У Go-версії Casbin можна використовувати інші назви та порядок; тоді після створення ефорсера потрібно викликати e.SetFieldIndex("p", constant.SubjectIndex, index), щоб такі API, як DeleteUser, використовували правильний стовпець.

# `subject` here is for sub
[policy_definition]
p =  obj, act, subject
e.SetFieldIndex("p", constant.SubjectIndex, 2) // index starts from 0
ok, err := e.DeleteUser("alice") // without SetFieldIndex, it will raise an error

Іменовані системи ролей та залежності дозволів​

g, g2, g3, ... — це незалежні системи ролей. Кожна з них визначає граф, який matcher викликає за тим самим ім’ям; g2 не є вбудованим відношенням «дозвіл залежить від дозволу». Такий рядок, як g2, edit, read, є лише ребром — він впливає на рішення тільки якщо matcher запитує g2(...).

Це важливо, коли ваш каталог дозволів має залежності, наприклад «edit передбачає read», тому роль, яка може редагувати, також повинна мати дозвіл на читання. Існує два чистих способи моделювання цього.

Використовуйте спадкування ролей, якщо залежність є частиною авторизації. Присвойте кожній групі дозволів роль і налаштуйте спадкування ролей:

p, editor, article, edit
p, viewer, article, read

g, editor, viewer
g, alice, editor

alice може читати, оскільки editor успадковує viewer; g2 тут не залучено.

Використовуйте окремий граф g2, якщо сама залежність має бути в політиці. Matcher визначає значення:

[role_definition]
g = _, _
g2 = _, _

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && (r.act == p.act || g2(p.act, r.act))
p, admin, article, write
g2, write, read
g, alice, admin

Запит alice, article, read відповідає рядку p, admin, article, write, оскільки g2(write, read) істинне: write є дочірнім елементом read, у тому ж напрямку, що й ребра g. Рядки g2 самі по собі нічого не надають і не валідуються Casbin; ви визначаєте напрямок і значення кожного ребра, тоді як Casbin застосовує той самий транзитивний механізм успадкування, що й для g.

Якщо залежність є лише метаданими каталогу — наприклад, роль editor повинна попередньо вибирати "read" в інтерфейсі адміністратора, коли хтось позначає "edit" — зберігайте її в каталозі дозволів і розгортайте в рядки p, g або g2 під час генерації політики. Casbin не потребує зберігання даних, які ніколи не оцінюються. Політика також не обов’язково має жити в CSV-файлі: адаптер може завантажувати згенеровані рядки з бази даних або з вашого YAML/JSON-каталогу, тому каталог залишається джерелом правди. Див. Адаптери щодо API адаптера.

Ієрархія ролей​

Casbin реалізує ієрархію ролей у стилі RBAC1: якщо alice має role1, а role1 має role2, то фактично alice має role2 та його дозволи.

Глибина ієрархії — це кількість рівнів успадкування, які ви дозволяєте. Менеджер ролей за замовчуванням використовує максимальну глибину 10 (конфігуровано), тому користувач може успадковувати ролі до 10 рівнів.

// NewRoleManager is the constructor for creating an instance of the
// default RoleManager implementation.
func NewRoleManager(maxHierarchyLevel int) rbac.RoleManager {
    rm := RoleManager{}
    rm.allRoles = &sync.Map{}
    rm.maxHierarchyLevel = maxHierarchyLevel
    rm.hasPattern = false

    return &rm
}

Розрізнення користувачів і ролей​

In Casbin, users and roles are both strings. In flat RBAC (no role hierarchy), GetAllSubjects() and GetAllRoles() return the left and right sides of g rules (often users and roles). With a hierarchy, the same name can appear as both user and role.

Оскільки імена є звичайними рядками, дві сутності різних типів з однаковим іменем вважаються одним суб'єктом. Коли імена надходять від користувачів, це створює ризик ескалації привілеїв: користувач, який зареєструється як admins, отримає всі дозволи групи admins, а організація з іменем acme_t_dev отримає дозволи команди dev в acme, якщо імена команд формуються за шаблоном <org>_t_<team>.

Використовуйте TypedName, щоб присвоїти кожному імені його тип. Різні типи або частини завжди дають різні імена, оскільки символи %, : та / всередині них екрануються:

casbin.TypedName("user", "admins")      // user:admins
casbin.TypedName("group", "admins")     // group:admins
casbin.TypedName("team", "acme", "dev") // team:acme/dev
casbin.TypedName("org", "acme_t_dev")   // org:acme_t_dev
casbin.TypedName("org", "acme/dev")     // org:acme%2Fdev

Використовуйте типізовані імена як при записі політик, так і при виконанні перевірок (enforce):

e.AddPolicy(casbin.TypedName("group", "admins"), "data1", "write")
e.AddGroupingPolicy(casbin.TypedName("user", "bob"), casbin.TypedName("group", "admins"))

ok, err := e.Enforce(casbin.TypedName("user", username), "data1", "write")

Функція ParseTypedName повертає тип та частини типізованого імені, а FilterTypedNames залишає лише імена певного типу, наприклад, команди серед ролей користувача:

roles, err := e.GetImplicitRolesForUser(casbin.TypedName("user", "bob"))
teams := casbin.FilterTypedNames(roles, "team")

Неявні ролі та дозволи​

Ролі та дозволи, успадковані через ієрархію (а не лише прямі призначення), називаються неявними. Використовуйте GetImplicitRolesForUser() і GetImplicitPermissionsForUser(), щоб включити їх; GetRolesForUser() і GetPermissionsForUser() повертають лише прямі призначення. Див. GitHub #137.

FAQ​

Що означає абревіатура RBAC? Role-based access control (контроль доступу на основі ролей). Дозволи прив’язані до ролей, користувачам призначаються ролі, а запит дозволяється, якщо одна з ролей користувача має відповідний дозвіл.

Який приклад використання RBAC? У наведеній вище програмі для роботи з документами роль viewer може читати статті, а роль editor — редагувати їх. Надання alice ролі editor дозволяє їй читати та редагувати, оскільки editor успадковує права від viewer; bob, який має роль viewer, може лише читати. Жоден дозвіл не надається alice чи bob безпосередньо.

Які існують типи RBAC? Сімейство RBAC96 описує чотири рівні: RBAC0 включає користувачів, ролі та дозволи; RBAC1 додає ієрархію ролей; RBAC2 додає обмеження, такі як розділення обов’язків; RBAC3 поєднує обидва підходи. Casbin реалізує RBAC0 та RBAC1, а обмеження виражаються у вигляді рядків політики або забезпечуються додатком. Див. RBAC vs. RBAC96.

Чи кращий RBAC за ABAC? Жодна модель не є кращою загалом. RBAC легше аудитувати, оскільки роль вказує, що вона дозволяє та хто її має, але для виразу "тільки свої записи" потрібна окрема роль для кожного запису. ABAC оцінює умови щодо атрибутів, таких як власник, відділ або час доби, і більшість додатків використовують ролі для функцій, а умови атрибутів — для записів.

Чи актуальний ще RBAC? Так. Ролі залишаються стандартним способом моделювання того, до яких функцій може отримати доступ користувач: NIST формалізував RBAC у 1990-х роках, і маппінг груп SSO та ролі IAM у хмарних сервісах досі дотримуються цієї моделі. ReBAC розширює її, коли спільний доступ налаштовується на рівні ресурсу, а не ролі; він не замінює RBAC.

Як додати RBAC до додатка? Використовуйте бібліотеку авторизації замість жорсткого кодування перевірок ролей. У Casbin модель — це конфігураційний файл, а політика — дані, тому ролі та дозволи можна змінювати без повторного розгортання. Повні приклади наведено в підручниках для Go, Node.js, Python та Java.

Умови використання

Apache Casbin (Incubating) — це проєкт, який проходить інкубацію в Apache Software Foundation (ASF) під егідою Apache Incubator. Інкубація є обов'язковою для всіх щойно прийнятих проєктів, доки подальший огляд не покаже, що інфраструктура, комунікації та процеси прийняття рішень стабілізувалися відповідно до інших успішних проєктів ASF. Хоча статус інкубації не обов'язково відображає повноту або стабільність коду, він свідчить про те, що проєкт ще не отримав повного схвалення з боку ASF.
