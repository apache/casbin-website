Що таке ReBAC? Контроль доступу на основі зв'язків із прикладами

Що таке ReBAC?​

Контроль доступу на основі зв'язків (ReBAC) визначає доступ на основі зв'язків між користувачами та ресурсами: alice є власником документа, bob — його глядачем, документ знаходиться в папці, папка належить команді. Правила пишуться один раз для кожного типу зв'язку, наприклад "власники можуть редагувати, глядачі можуть читати", і кожен користувач отримує доступ через зв'язки, записані для нього.

Типові питання, на які відповідає ReBAC:

  • Чи є користувач власником ресурсу?
  • Чи є користувач учасником проєкту, якому належить ресурс?
  • Чи належить ресурс до типу, до якого у користувача є доступ?

Це підходить для додатків, де спільне використання є частиною продукту: обмін документами та файлами, інструменти для співпраці, трекери проєктів, соціальні мережі та багатокористувацькі SaaS.

ReBAC і Google Zanzibar​

ReBAC став широко відомим завдяки статті Google про Zanzibar (USENIX ATC 2019) — систему, що стоїть за спільним використанням у Google Drive, Calendar та інших сервісах. Zanzibar зберігає зв'язки як кортежі об'єкта, зв'язку та користувача, наприклад doc:design.md#viewer@user:bob. Відкриті сервіси, такі як OpenFGA та SpiceDB, дотримуються того ж дизайну. У Casbin той самий факт є одним рядком політики, g, bob, design.md, viewer, а зіставлювач моделі визначає, що дозволяє кожен зв'язок.

ReBAC проти RBAC проти ABAC​

Доступ походить відПриклад правила
RBACРоль користувача, однакова для кожного ресурсуредактори можуть редагувати документи
ReBACЗв'язок користувача з цим конкретним ресурсомвласник документа може редагувати його
ABACАтрибути користувача, ресурсу та середовищалюди з відділу документа можуть читати його в робочий час

RBAC з роллю для кожного ресурсу ("alice є редактором для doc1") вже є простою формою ReBAC, саме так Casbin моделює це нижче. Вибір моделі контролю доступу розбирає один приклад у кожній моделі та порівнює їх пліч-о-пліч.

ReBAC у Casbin​

Casbin моделює ReBAC за допомогою:

  • Зв'язків користувач–ресурс–роль: "користувач U має роль R для ресурсу O" (наприклад, alice є collaborator для doc1).
  • Зв'язків ресурс–тип: "ресурс O є типу T" (наприклад, doc1 є типу doc).

Дозволи тоді виглядають як "роль R може виконувати дію A для типу T"; користувач отримує дозвіл, якщо він має R для ресурсу, який є типу T. Приклад моделі:

[request_definition]
r = sub, obj, act

[policy_definition]
p = role, obj_type, act

[role_definition]
g = _, _, _
g2 = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, r.obj, p.role) && g2(r.obj, p.obj_type) && r.act == p.act
# Permission definition: The "collaborator" role can read files of type "doc"
p, collaborator, doc, read

# User-Resource-Role Relationship: alice is a collaborator of doc1
g, alice, doc1, collaborator

# Resource-Type Relationship: doc1 is of type "doc"
g2, doc1, doc

Отже: користувач повинен мати правильну роль для ресурсу, а ресурс повинен відповідати типу в правилі дозволу. Casbin комбінує g (користувач–ресурс–роль), g2 (ресурс–тип) та p (роль–тип–дія), щоб визначити доступ.

FAQ​

Чи потрібен мені сервіс у стилі Zanzibar для використання ReBAC? Ні. Якщо зв'язки поміщаються в базі даних вашого додатка і перевірки відбуваються всередині вашого сервісу, бібліотеки на кшталт Casbin достатньо. Виділений сервіс має сенс, коли багато сервісів повинні ділити одне сховище зв'язків; див. Casbin vs. OpenFGA.

Чи можу я спробувати цю модель без написання коду? Так. Оберіть приклад ReBAC у онлайн-редакторі.

Умови використання

Apache Casbin (Incubating) — це проєкт, який проходить інкубацію в Apache Software Foundation (ASF) під егідою Apache Incubator. Інкубація є обов'язковою для всіх щойно прийнятих проєктів, доки подальший огляд не покаже, що інфраструктура, комунікації та процеси прийняття рішень стабілізувалися відповідно до інших успішних проєктів ASF. Хоча статус інкубації не обов'язково відображає повноту або стабільність коду, він свідчить про те, що проєкт ще не отримав повного схвалення з боку ASF.
