Meningkatkan Casbin (Go) dari v2 ke v3: Panduan Migrasi Lengkap

1 Februari 2026 · Dibaca dalam 1 menit
Yang Luo
Creator of Casbin

Jika Anda menjalankan Casbin v2 di produksi dan bertanya-tanya tentang jalur peningkatan ke v3, panduan ini ditujukan untuk Anda. Kami akan membahas semua yang perlu Anda ketahui tentang transisi, mulai dari memahami apa yang berubah hingga melakukan migrasi produksi dengan aman.

What Changed in v3?​

Kabar baiknya: v3 terutama adalah perubahan path modul dengan kompatibilitas mundur penuh. Logika otorisasi inti, API, dan fungsionalitas tetap tidak berubah. Ini adalah keputusan yang disengaja untuk meminimalkan gangguan sambil mengikuti konvensi versioning semantik Go.

The Main Change: Module Path​

Satu-satunya perubahan yang merusak (breaking change) dalam v3 adalah path modul Go:

// v2
import "github.com/casbin/casbin/v2"

// v3
import "github.com/casbin/casbin/v3"

Itu saja. Kebijakan, model, dan logika kode Anda yang ada tidak perlu diubah. Migrasinya bersifat mekanis: perbarui pernyataan import dan file go.mod Anda.

Why Release v3?​

Anda mungkin bertanya-tanya mengapa merilis versi mayor baru hanya untuk perubahan path import. Jawabannya adalah versioning semantik. Sistem modul Go menggunakan nomor versi mayor dalam path import (/v2, /v3, dst.). Hal ini memungkinkan beberapa versi mayor untuk hidup berdampingan dalam pohon dependensi yang sama, yang krusial untuk aplikasi besar dengan banyak dependensi.

Dengan merilis v3, kami telah:

  • Menyelaraskan dengan versioning import semantik Go
  • Memungkinkan migrasi bertahap dalam graf dependensi yang kompleks
  • Menyiapkan panggung untuk peningkatan masa depan tanpa mengganggu pengguna v2 yang ada

What Stayed the Same?​

Semua hal lainnya. Serius.

  • Semua API tetap identik - Enforce(), AddPolicy(), GetAllRoles(), dan metode lainnya bekerja persis seperti sebelumnya
  • Sintaks model dan kebijakan tidak berubah - File model .conf dan file kebijakan .csv Anda yang ada berfungsi tanpa modifikasi
  • Antarmuka adapter tidak berubah - Metode persist.Adapter tetap sama; adapter hanya memerlukan rilis yang dibangun terhadap path modul v3
  • Karakteristik kinerja - Tidak ada regresi atau peningkatan kinerja; mesinnya tetap sama
  • Integrasi middleware - Middleware bekerja dengan cara yang sama setelah mengimpor versi mayor yang sama dengan enforcer Anda

New Features in v3​

Sejak rilis v3.0.0 pada Desember 2025, beberapa fitur baru telah ditambahkan:

v3.7.0+: Enhanced Logger Integration​

Anda sekarang dapat mengintegrasikan logger kustom ke dalam operasi penegakan dan manajemen kebijakan inti Casbin, memberikan observabilitas yang lebih baik:

enforcer.SetLogger(yourCustomLogger)

v3.8.0+: GetAllUsers() API​

API baru untuk membedakan pengguna dari peran:

users, err := enforcer.GetAllUsers()

Ini sangat berguna dalam sistem RBAC di mana Anda perlu mencantumkan pengguna aktual secara terpisah dari definisi peran.

v3.9.0+: Built-in Cycle Detection​

Enforcer kini menyertakan deteksi otomatis siklus dalam hierarki peran, mencegah loop tak terbatas:

// Automatically detects and prevents circular role assignments
enforcer.AddGroupingPolicy("alice", "admin")
enforcer.AddGroupingPolicy("admin", "alice") // Will be detected as a cycle

v3.10.0+: Explain() API for AI-Powered Authorization Insights​

Fitur terbaru memanfaatkan API LLM untuk menjelaskan keputusan otorisasi dalam bahasa alami:

enforcer.SetAIConfig(casbin.AIConfig{
    Endpoint: "https://api.openai.com/v1/chat/completions",
    APIKey:   os.Getenv("OPENAI_API_KEY"),
    Model:    "gpt-4",
})

explanation, err := enforcer.Explain("alice", "data1", "read")
// e.g. "Alice can read data1 because she has the 'reader' role..."

Ini sangat berharga untuk men-debug kebijakan kompleks dan membantu pemangku kepentingan non-teknis memahami keputusan otorisasi.

Strategi Migrasi​

Untuk Proyek Baru​

Sederhana: cukup gunakan v3 sejak awal.

go get github.com/casbin/casbin/v3
import "github.com/casbin/casbin/v3"

Untuk Proyek v2 yang Sudah Ada​

Migrasi ini melibatkan tiga langkah:

Langkah 1: Perbarui go.mod Anda​

go get github.com/casbin/casbin/v3
go mod tidy

Langkah 2: Perbarui Pernyataan Impor​

Temukan dan ganti semua impor Casbin di seluruh basis kode Anda:

# Using sed on Unix/Linux/Mac
find . -type f -name '*.go' -exec sed -i 's|github.com/casbin/casbin/v2|github.com/casbin/casbin/v3|g' {} +

# Or manually in your editor
# Find: github.com/casbin/casbin/v2
# Replace: github.com/casbin/casbin/v3

Langkah 3: Perbarui Impor Adapter (Jika Berlaku)​

Sebuah adapter mengimplementasikan persist.Adapter dari satu versi utama tertentu, karena model.Model di casbin/v2 dan casbin/v3 adalah tipe Go yang berbeda. Oleh karena itu, enforcer v3 memerlukan rilis adapter yang mengimpor github.com/casbin/casbin/v3. Periksa go.mod adapter tersebut:

// Example: the PostgreSQL adapter already depends on casbin/v3
import pgadapter "github.com/apache/casbin-pg-adapter"

// The file adapter is built in and ships with each major version

Jika adapter Anda belum diperbarui, tetaplah menggunakan v2 untuk layanan tersebut hingga adapter diperbarui, atau buka isu di repositori adapter tersebut.

Rencana Rollback​

Jika Anda perlu melakukan rollback:

  1. Level Kode: Kembalikan perubahan impor (gunakan kontrol versi)
  2. Level Dependensi: go get github.com/casbin/casbin/v2@latest
  3. Deployment: Gunakan proses deployment standar Anda untuk mengembalikan keadaan

Keindahan dari migrasi ini adalah bahwa rollback sangat mudah - cukup kembalikan perubahan impor dan deploy ulang.

Apakah Saya Perlu Memigrasikan Database Kebijakan Saya?​

Tidak. Data kebijakan yang ada tetap tidak berubah. Kebijakan disimpan sebagai string sederhana (subjek, objek, aksi, dll.) dan tidak memiliki ketergantungan pada versi Casbin.

Menguji Migrasi Anda​

Pengujian Otomatis​

Tes yang sudah ada seharusnya lolos tanpa modifikasi:

func TestPolicyEnforcement(t *testing.T) {
    // This test works identically in v2 and v3
    e, _ := casbin.NewEnforcer("model.conf", "policy.csv")
    
    ok, _ := e.Enforce("alice", "data1", "read")
    if !ok {
        t.Error("Expected alice to have read access to data1")
    }
}

Pengujian Integrasi​

Middleware yang mengambil *casbin.Enforcer terikat pada satu versi utama dengan cara yang sama seperti adapter. Jika middleware Anda masih mengimpor casbin/v2, memanggil enforcer secara langsung hanya membutuhkan beberapa baris kode:

// Example with Gin
import (
    "net/http"

    "github.com/casbin/casbin/v3"
    "github.com/gin-gonic/gin"
)

func Authorizer(e *casbin.Enforcer) gin.HandlerFunc {
    return func(c *gin.Context) {
        ok, err := e.Enforce(c.GetString("user"), c.Request.URL.Path, c.Request.Method)
        if err != nil || !ok {
            c.AbortWithStatus(http.StatusForbidden)
            return
        }
        c.Next()
    }
}

Pengujian Beban​

Jalankan tes beban standar Anda terhadap build v3. Karakteristik kinerja harus identik dengan v2.

Verifikasi Kebijakan​

Bandingkan evaluasi kebijakan antar versi:

# Export policies from v2
# Load into v3
# Run test cases against both
# Compare results

Jika Anda melihat adanya perbedaan, kemungkinan besar itu adalah bug - silakan laporkan!

Kesalahan Umum​

Kesalahan 1: Campuran Dependensi v2/v3​

Masalah: Beberapa dependensi menggunakan Casbin v2, yang lain menggunakan v3, sehingga menyebabkan konflik.

Solusi: Build itu sendiri aman: sistem modul Go memperlakukan v2 dan v3 sebagai paket terpisah, sehingga keduanya dapat berada dalam pohon dependensi yang sama. Yang tidak dapat Anda lakukan adalah meneruskan enforcer v3 ke pustaka yang mengharapkan enforcer v2. Pastikan enforcer, adapter-nya, dan middleware-nya berada pada versi utama yang sama.

Kesalahan 2: Ketidakcocokan Versi Adapter​

Masalah: Menggunakan adapter v2 dengan Casbin v3 (atau sebaliknya).

Solusi: Ini akan muncul sebagai kesalahan kompilasi, bukan kejutan saat runtime. Periksa versi utama Casbin yang dibutuhkan oleh go.mod adapter dan gunakan rilis yang cocok dengan enforcer Anda.

Kesalahan 3: Lupa Paket Internal​

Masalah: Memperbarui impor aplikasi utama tetapi lupa paket internal atau alat bantu.

Solusi: Gunakan go mod graph dan go mod why untuk menemukan semua dependensi Casbin:

go mod graph | grep casbin

Kesalahan 4: Masalah Kompilasi Adapter Kustom​

Masalah: Adapter kustom tidak dapat dikompilasi setelah upgrade.

Solusi: Antarmuka adapter tidak berubah, sehingga ini menunjukkan adanya masalah impor. Pastikan semua impor Casbin di adapter Anda menggunakan v3:

import (
    "github.com/casbin/casbin/v3"
    "github.com/casbin/casbin/v3/persist"
)

FAQ​

Q: Apakah v2 masih dipelihara?​

Pada saat penulisan ini, v2 menerima perbaikan bug kritis, tetapi fitur baru dikembangkan untuk v3. Rencanakan migrasi dalam 6-12 bulan ke depan.

Q: Bisakah saya bermigrasi secara bertahap dengan memiliki beberapa layanan di v2 dan yang lainnya di v3?​

Ya! Keduanya bahkan dapat berbagi basis data kebijakan yang sama. Ini adalah salah satu keuntungan dari perubahan minimal di v3.

Q: Akankah middleware saya (Gin, Echo, Fiber, dll.) berfungsi?​

Hanya jika middleware tersebut mengimpor versi mayor yang sama dengan enforcer Anda. Periksa go.mod middleware; jika masih menggunakan v2, panggil Enforce() dari handler kecil milik Anda sendiri seperti yang ditunjukkan di atas.

Q: Apakah saya perlu memperbarui file model .conf saya?​

Tidak. Sintaks file model tidak berubah.

Q: Apakah saya perlu memperbarui file kebijakan .csv saya?​

Tidak. Format file kebijakan tidak berubah.

Q: Bagaimana dengan WatcherEx, FilteredAdapter, dan antarmuka lainnya?​

Semua antarmuka tetap tidak berubah. Jika kode Anda mengimplementasikan antarmuka ini, tidak ada modifikasi yang diperlukan (selain jalur impor).

Q: Dampak terhadap kinerja?​

Tidak ada. v3 menggunakan mesin evaluasi yang sama dengan v2.

Q: Bisakah saya menggunakan v3 dengan Go 1.16?​

Periksa go.mod di repositori Casbin v3 untuk mengetahui versi Go minimum yang didukung. Secara umum, disarankan untuk menggunakan versi stabil terbaru dari Go.

Selamat melakukan upgrade!

Apache Casbin (Incubating) adalah upaya yang sedang mengalami inkubasi di The Apache Software Foundation (ASF), disponsori oleh Apache Incubator. Meskipun status inkubasi tidak selalu mencerminkan kelengkapan atau stabilitas kode, hal itu menunjukkan bahwa proyek tersebut belum sepenuhnya didukung oleh ASF.
